# GLM 5.3 prefix-cache reuse restored by prompt-rendering fixes

## Executive summary

GLM 5.3 prefill prefix-cache reuse increased from 59% during the morning workload, and 74% during the preceding lighter overnight period, to 96% after two vLLM prompt-rendering fixes. The first fix corrected Claude Code inline-system-reminder placement on `/v1/messages`; the second stripped a request-varying `cch` billing header from the system prompt on the Chat Completions path used through LiteLLM.

The router was not the main source of lost reuse. Its predicted hit rate tracked engine-delivered reuse within 0.1 percentage point. The dominant loss happened before routing could help: semantically incidental text was changing the beginning of the rendered prompt, making prior-turn KV prefixes unusable.

Reported prefill compute per prompt token fell from 0.41 to 0.04. Paid streaming TTFT p90 fell from 7.2 seconds to 4.6 seconds. The final figures came from a 16-minute window at lower load than the morning baseline, so a busy-hour validation remains pending.

## Validity verdict: Conditionally valid

The prompt-rendering diagnosis and prefix-reuse recovery are supported by:

- two identified mechanisms that change the prompt prefix;
- stepwise reuse improvement as each fix went live;
- close agreement between router-predicted and engine-delivered reuse;
- the expected reduction in prefill compute.

The end-to-end TTFT comparison is not yet a controlled busy-hour comparison. The after window was shorter and lighter than the 59% morning baseline. It supports the improvement direction but cannot isolate the size of the latency benefit from load.

No raw time series, run identifiers, exact request counts, concurrency, or workload mix were included in the update. Those are required before treating the result as a completed benchmark.

## Main takeaways

- **Measured:** reuse reached 96% after both prompt-rendering fixes, up 37 percentage points from the 59% morning snapshot and 22 points from the 74% overnight snapshot.
- **Measured:** the first fix moved reuse to 80%; the second moved it from 80% to 96%.
- **Measured:** reported prefill compute per prompt token fell by approximately 90.2%, from 0.41 to 0.04, or to about one tenth of its prior value.
- **Measured:** paid streaming TTFT p90 fell 2.6 seconds, from 7.2 to 4.6 seconds, a 36.1% relative reduction in the reported windows.
- **Observation:** router-predicted reuse and engine-delivered reuse agreed within 0.1 percentage point, indicating that placement was already close to the available optimum.
- **Inference:** prompt canonicalization is a first-order cache-performance feature for agentic multi-turn traffic. A routing algorithm cannot recover reuse after rendering moves volatile text to token zero.
- **Open:** repeat the comparison under matched busy-hour load before using the TTFT delta as a capacity or SLO planning value.

## Root cause and fixes

### `/v1/messages`: inline system reminders moved to the prompt start

Claude Code sessions were recomputing most of the conversation on every turn. In vLLM 0.30, inline system reminders were moved to the beginning of the rendered prompt. Because each reminder could change, the prompt diverged at its start and invalidated reuse of the preceding conversation.

A `--chat-template` override correcting the placement went live at 09:03Z. The upstream correction is [vLLM PR 58754](https://github.com/vllm-project/vllm/pull/58754), reported as included in v0.31.0rc1.

Reported reuse after this first fix was 80%.

### `/v1/chat/completions`: volatile `cch` billing header

Claude Code traffic passing through LiteLLM used Chat Completions. Its system prompt began with a billing header containing a `cch` value that changed on every request. That placed request-varying text at the first tokens and prevented one turn from reusing the previous turn.

vLLM already stripped this material on `/v1/messages`, but not on the Chat Completions path. A local patch went live at 11:06Z, and [vLLM PR 59419](https://github.com/vllm-project/vllm/pull/59419) was opened upstream.

Reported reuse after both fixes was 96%.

## Why routing was not the primary loss

Router placement was described as close to the best achievable. Its predicted hit rate tracked the cache reuse delivered by engines within 0.1 percentage point.

This distinguishes two failure classes:

1. **rendering failure:** equivalent conversations produce different leading tokens, so no endpoint has the desired prefix;
2. **placement failure:** an endpoint has the prefix, but the router sends the request elsewhere.

The incident was primarily the first class. Improving placement alone would not recover a prefix that rendering had destroyed.

## Functional and system regression coverage

These fixes define specific regression tests.

### RENDER-PREFIX-MSG-001 — Claude Code reminder stability

Use two sanitized Claude Code-shaped `/v1/messages` requests representing consecutive turns. Change only an inline system reminder that should remain near its semantic location rather than moving to token zero.

Render both requests through the deployed vLLM render path and assert:

- the token prefix representing the stable system prompt and prior conversation is unchanged;
- the first differing token occurs no earlier than the expected reminder location;
- the second request extends the reusable prefix instead of replacing it;
- the result is identical through direct vLLM and the router's native Messages render path.

The fixture must be captured from a real affected request shape and sanitized. A generic system message may not reproduce the regression.

### RENDER-PREFIX-CHAT-001 — volatile billing-header normalization

Use two Chat Completions requests identical except for the `cch` value in the real billing-header shape.

Assert:

- rendered tokens are identical after normalization;
- the billing metadata does not appear at the beginning of the rendered prompt;
- direct vLLM, router rendering, and the LiteLLM path preserve the intended normalization;
- a semantically meaningful system-prompt change still changes the rendered tokens, proving the test is not stripping the entire system message.

### CACHE-ROUTER-001 — predicted versus delivered reuse

Under a controlled multi-turn replay, compare router-predicted prefix hit with engine-delivered reuse for the selected prefill rank.

Assert the absolute difference stays within a profile-declared tolerance. The 0.1 percentage-point agreement in this update is an observed result, not yet a universal threshold.

This requires router and engine telemetry and is therefore a system-integrated test.

### CACHE-RESTART-001 — router snapshot recovery

Warm prefixes on multiple prefill engines, restart or replace the router in a non-production environment, and assert:

- snapshots repopulate the shared index within a declared recovery time;
- predicted-hit coverage returns without replaying the full traffic history;
- early post-restart requests do not regress to random placement beyond the declared allowance.

### CACHE-RESP-001 — Responses prefix scoring

Send two `/v1/responses` requests with a shared prefix and assert the router assigns a prefix score and routes using it. A successful response alone is insufficient because the request can pass through without payload-aware scoring.

### CACHE-PD-METRIC-001 — prefill-rank attribution

In a P/D deployment, assert predicted-hit metrics identify the prefill rank that owns or is expected to reuse the prefix. This protects against recording the metric on the decode rank and falsely diagnosing placement.

## Conclusion

The update establishes that prompt rendering, rather than router placement, caused most of the lost GLM 5.3 prefix reuse for the observed Claude Code traffic. Both the native Messages path and the LiteLLM-to-Chat-Completions path needed normalization fixes.

The 96% reuse result and large compute reduction are operationally meaningful. The next decision-quality step is a matched busy-hour measurement with the same traffic mix, duration, and component versions, plus raw router-predicted and engine-delivered reuse series.
