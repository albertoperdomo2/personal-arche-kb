# 2026-07-21 — AgentX C32 U0.55 vLLM 0.23 offload-tier matrix

## Executive conclusion

This batch demonstrates a **large CPU-offload benefit**, a **capacity-matched CPU64+NVMe gain**, and now **two CephFS write-drain failures**. The added log-capture run is not evidence that collecting logs slowed inference: collection started after the benchmark. It is a second, worse observation of the same tiering-backpressure mechanism on a different GPU node.

- Adding a 64 GiB CPU tier raised successful request throughput from **0.578 to 1.174 requests/s (+103.1%)**, doubled output-token throughput, reduced mean TTFT by **54.8%**, and reduced mean end-to-end latency by **48.8%**.
- The corrected 64 GiB CPU+NVMe run was fastest at **1.298 requests/s**, +10.5% over CPU64. Mean TTFT fell **29.8%**, mean end-to-end latency fell **22.2%**, and completed AgentX sessions rose from **41 to 44**. External KV supplied **88.9%** of prompt tokens versus 77.3% for CPU-only. Node telemetry observed **459.8 GiB read** and **381.5 GiB written**, while NVMe busy time averaged only **13.5%**. This is materially stronger evidence for useful NVMe readback than the superseded cell.
- CPU64+CephFS was -12.2% slower than the matched CPU64 run. It began refusing stores **12.31 minutes** into profiling and produced **102,325** `cannot store blocks` warnings across **812** request IDs. After that point, external-KV prompt rate fell **67.7%** and local-compute prompt rate grew **4.0×**. This is the direct reason CephFS lost ground.
- The added CephFS observation reached only **0.732 requests/s**, **-29.0%** versus the first Ceph run and **-37.6%** versus CPU64. External KV supplied only **41.4%** of prompt tokens, while local recomputation rose to **53.6%**. Its retained log contains at least **153,743** store-refusal warnings, but the file is a **24.87 MB tail** with startup and early profiling missing, so warning onset and total are lower bounds.
- This is a tail-collapse result, not a different easy/hard trace draw. **1,316** completed requests pair by deterministic AgentX `conversation_id`, turn, and depth; p95 prompt-length difference is only **3 tokens**. For those same requests, p99 E2E latency grew from **108.2 to 454.2 seconds**, while the maximum reached **1104.3 seconds**. Those stalls reduced offered load: only 55 sessions were sent and 25 completed, versus 69 and 39 in the first Ceph run.
- Concurrency 32 at U=0.55 is already enough to expose tier behavior. The original four cells averaged 92.1–94.6% GPU-KV occupancy; the added Ceph run fell to **79.6%** because stalled AgentX sessions stopped feeding enough runnable requests. Raising concurrency would hide the backpressure symptom behind more queueing rather than repair it.

**Disposition:** accept no-offload↔CPU64 as strong directional evidence and CPU64↔CPU64+NVMe as a credible but not yet publication-grade NVMe result. Reject both CephFS observations as healthy performance cells. The repeated high-level failure is established; the lower-level variation between the two Ceph runs remains attributed to the changed node and/or time-varying CephFS client/metadata service because direct Ceph I/O telemetry is absent.

## Why CPU offload helps

Figure 3 separates prompt tokens by server-side source. No-offload locally computed **97.2%**. CPU64 served **77.3%** through external KV transfer; CPU64+NVMe raised that to **88.9%**. The first Ceph run reached **64.9%**, while the added Ceph observation fell to **41.4% external** and **53.6% local compute**, despite the highest theoretical AgentX reuse at 94.24%. The lost throughput is therefore observed recomputation, not lack of reusable prefixes.

For each 15-second sample, the external share is

$$
s_{\mathrm{external}}(t)=
\frac{r_{\mathrm{external}}(t)}
{r_{\mathrm{external}}(t)+r_{\mathrm{GPU\ hit}}(t)+r_{\mathrm{compute}}(t)}.
$$

## CephFS: active, but unable to drain stores

The first Ceph observation proves filesystem allocation: its fresh 3 TiB PVC eventually reported **206,577,860,608 bytes = 192.39 GiB** used. The added observation also received a newly provisioned PVC, but its kubelet volume-stat query stayed at zero and every Ceph pool/MDS/OSD query returned zero series. Thus direct filesystem bytes are unavailable for the new run; vLLM's configured tier, external-load behavior, and store-refusal path establish the mechanism but not an exact CephFS hit/read count.

Neither pod restarted or OOMed, and neither log contains `No space left`, short read/write, permission, or block-I/O exceptions. The first run had two `ServerDisconnectedError`s; the new one had one `ClientPayloadError` at minute 19.4. Those sparse connection errors cannot explain hundreds of missing completions.

### Why the log-capture change is not the cause

The benchmark job completed before the artifact-collection pod was created and started. Log collection is therefore post-run work. The new model-log artifact is **24,874,306 bytes**, starts at 14:13:07 rather than server startup, and contains only the final ten profiling minutes plus teardown. Its **153,743** profiling warnings and minute-20 “onset” are lower bounds created by tail retention, not evidence that the failure began at minute 20. The attempt to capture logs revealed the flood; it did not create it.

The failure is in the vLLM tiering backpressure path:

1. The [vLLM v0.23 scheduler](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/distributed/kv_transfer/kv_connector/v1/offloading/scheduler.py#L796-L803) prints `cannot store blocks` only when `manager.prepare_store(...)` returns `None`.
2. The [CPU primary manager](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/v1/kv_offload/cpu/manager.py#L151-L177) returns `None` when it needs space but cannot evict enough blocks.
3. In the [tiering manager](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/v1/kv_offload/tiering/manager.py#L490-L536), a completed GPU-to-CPU store is cascaded to every secondary tier; `primary.prepare_read()` increments the CPU block reference count, pinning that block until the asynchronous secondary job completes.
4. The [filesystem tier](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/v1/kv_offload/tiering/fs/manager.py) writes one block file per key through a dual-queue thread pool. Slow or backlogged CephFS writes therefore leave too many CPU blocks referenced and non-evictable.

The backlog condition can be expressed as

$$
\frac{dB}{dt}=R_{\mathrm{store\ submitted}}-R_{\mathrm{store\ completed}}.
$$

When $dB/dt>0$ for long enough, in-flight secondary writes pin the finite primary CPU tier. The complete first-run log crosses that point at 12.31 minutes. Its warning count is a scheduler retry count, not 102,325 unique failed blocks: 812 request IDs were affected and one request was retried 5,012 times. The truncated second log contains at least 153,743 profiling retries across 459 visible request IDs; one visible request was retried 3,184 times.

The scheduler gauges show the consequence: CephFS averaged **22.84 waiting requests** versus **17.27** for CPU-only and reached 51 versus 44. It also carried more effective prefill concurrency (23.13 versus 17.48), consistent with recomputation replacing reusable external loads.

Figure 7 supplies temporal corroboration. In the first Ceph run, CPU→GPU bandwidth fell about **66%** after the complete log's warning onset. The added run transfers only **1.17 TiB CPU→GPU** versus **2.34 TiB** in the first run and its external-token contribution falls more deeply. GPU↔CPU transfer cost was actually lower on the new node (about 0.020 versus 0.024–0.028 seconds/GiB), so the measured PCIe/CPU leg is not the slow component; the uninstrumented secondary filesystem leg remains the bottleneck class.

Provenance: vLLM native offload byte counters transformed to five-minute rates and sampled every 15 seconds. These counters cover GPU↔CPU transfers; they do not identify CPU↔filesystem bytes.

## Telemetry gaps

- GPU SM utilization, VRAM used/free, and PCIe RX/TX queries returned **zero series** for all runs. GPU KV-cache occupancy is available and is not a substitute for SM utilization.
- Ceph pool bytes/s, pool IOPS, MDS client operations, MDS memory, OSD latency, and Ceph health queries returned **zero series**. PVC usage proved allocation in the first Ceph run but stayed zero on the second node; no direct CephFS bandwidth or latency measurement exists for the added run.
- vLLM exposes GPU↔CPU offload counters but no per-secondary-tier hit, byte, latency, queue-depth, or in-flight-block metrics in these artifacts. Exact CephFS read hits therefore cannot be counted.
- `prefix_cache_hit_rate` archived as zero throughout, while prompt-token-source counters and AIPerf theoretical reuse were non-zero. It is not used for conclusions.
- The added 24.87 MB model log is a retained tail, not a complete log. Warning onset, total warnings, startup messages, and early filesystem-manager messages are unavailable.

## Acceptance decisions

### No offload versus CPU64 — accept directionally

The configuration difference is isolated, the connector is active, external token sourcing jumps from 0% to 77%, and every client metric improves by roughly 40–103%. The fixed-duration workload and tail censoring prevent a precise confidence interval, but not the direction of the result.

### CPU64+NVMe — accept directionally, repeat under exact controls

CPU capacity is now matched and NVMe traffic is real: 459.8 GiB read, 381.5 GiB written, 13.5% mean busy, zero request errors, and zero `cannot store blocks`. The 10.5% request-throughput, 29.8% TTFT, 22.2% E2E, and 7.3% completed-session improvements are credible directional evidence. Do not call them isolated NVMe effect sizes until `/dev/shm`, path cleanliness, hash seed, and repetitions are controlled.

### CPU64+CephFS — reject both observations as healthy performance cells

The first run proves CephFS allocation and the second repeats the store-admission failure with a worse external-reuse collapse and a fourfold p99 matched-latency tail. The collection step is post-benchmark, so logging did not cause the regression. Preserve both as failure experiments. The mechanism is secondary-tier drain/backpressure; the exact physical reason the second observation is worse is not identifiable because it moved nodes and has no CephFS client/daemon telemetry.

## Next experiment

1. **Repeat the corrected CPU64 pair under exact controls:** CPU64 and CPU64+NVMe with the same 200 GiB `/dev/shm`, release topology, U=0.55, C=32, TP=2, duration, and image digest.
2. **Clean every secondary tier and fix hashing:** use a run-scoped empty NVMe directory (or explicit pre-run deletion) and `PYTHONHASHSEED=0`; record clean-state proof. Run at least three paired seeds.
3. **Repeat Ceph on the same node with a fresh PVC:** pin `…-6kl5z` for a direct repeat, then `…-fx7c8`, with a newly named PVC per run and proof of empty state. Repeat each at least three times. This separates node/client-path variance from cluster-time variance.
4. **Make the Ceph acceptance gate mechanical:** zero `cannot store blocks`; no sustained filesystem store queue; stable external-token share; no p99 tail explosion; direct secondary read/write counters present. Increasing CPU to 96 or 128 GiB may buffer bursts, but it is not a fix unless secondary completion catches submission.
5. **Instrument the missing layer:** per-tier lookup hits/misses, bytes submitted/completed, transfer latency, queue depth, in-flight jobs/blocks, and store failures. Add pod-level Ceph client I/O, MDS/OSD metrics, and a log collector that retains the complete server log. Without these, exact CephFS hits and the node-specific slowdown remain unknowable.
6. **Test CephFS drain capacity:** sweep filesystem `n_write_threads` (default 16), measure completion throughput, and consider reducing file-per-block metadata pressure. Increase threads carefully; the goal is a stable completion rate, not merely a later failure.
7. **Keep AgentX for end-to-end relevance, add a mechanism control:** run at least three seeds per cell and report intervals. Pair it with a fixed request/reuse replay so each tier sees the same request arrival sequence. Report session completions and matched tail latency, not request throughput alone.

Do **not** raise concurrency yet. This C=32 run already kept the GPU KV cache near full and exposed Ceph backpressure. Do **not** lower GPU memory utilization further until Ceph store draining is fixed; U=0.55 already creates the intended offload pressure.

## Bottom line

The added run does not overturn the earlier conclusion; it strengthens it. CephFS-tier backpressure produces store-refusal floods, lower external reuse, more recomputation, and rare multi-minute stalls. Those stalls feed back through AgentX's closed loop until GPU-KV occupancy and offered load fall. Log collection occurred afterward and the completed prompts are pairwise comparable, so neither logging overhead nor workload selection is the root cause. The remaining unknown is why the filesystem leg drained even worse on `…-fx7c8` at that time; only a same-node repeated run with direct Ceph client/metadata telemetry can resolve that layer.
