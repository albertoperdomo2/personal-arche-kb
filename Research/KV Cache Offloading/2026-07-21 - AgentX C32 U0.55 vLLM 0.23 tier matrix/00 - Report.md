# 2026-07-21 — AgentX C32 U0.55 vLLM 0.23 offload-tier matrix

## Executive conclusion

This corrected batch demonstrates a **large CPU-offload benefit**, a **capacity-matched CPU64+NVMe gain**, and a **CephFS write-drain failure rather than a healthy CephFS performance point**.

- Adding a 64 GiB CPU tier raised successful request throughput from **0.578 to 1.174 requests/s (+103.1%)**, doubled output-token throughput, reduced mean TTFT by **54.8%**, and reduced mean end-to-end latency by **48.8%**.
- The corrected 64 GiB CPU+NVMe run was fastest at **1.298 requests/s**, +10.5% over CPU64. Mean TTFT fell **29.8%**, mean end-to-end latency fell **22.2%**, and completed AgentX sessions rose from **41 to 44**. External KV supplied **88.9%** of prompt tokens versus 77.3% for CPU-only. Node telemetry observed **459.8 GiB read** and **381.5 GiB written**, while NVMe busy time averaged only **13.5%**. This is materially stronger evidence for useful NVMe readback than the superseded cell.
- CPU64+CephFS was -12.2% slower than the matched CPU64 run. It began refusing stores **12.31 minutes** into profiling and produced **102,325** `cannot store blocks` warnings across **812** request IDs. After that point, external-KV prompt rate fell **67.7%** and local-compute prompt rate grew **4.0×**. This is the direct reason CephFS lost ground.
- Concurrency 32 at U=0.55 is already enough to expose tier behavior. GPU KV occupancy averaged **92.3–94.4%**. Increasing concurrency is unnecessary for this mechanism test and would mix queueing pressure into an already clear storage-backpressure signal.

**Disposition:** accept no-offload↔CPU64 as strong directional evidence and CPU64↔CPU64+NVMe as a credible but not yet publication-grade NVMe result. CPU capacity is now controlled, but `/dev/shm` (1 GiB versus 200 GiB), dirty host-path state, unset `PYTHONHASHSEED`, and single-run variance remain. Reject CPU64+CephFS as a healthy performance point while preserving it as a useful failure experiment.

## Why CPU offload helps

Figure 3 separates prompt tokens by their server-side source. No-offload locally computed **97.2%** of observed prompt tokens. CPU64 served **77.3%** through external KV transfer and locally computed 22.2%; CPU64+NVMe raised the external share to **88.9%** and cut local compute to 10.9%. These source metrics explain the throughput change more directly than theoretical AgentX reuse, which remained narrowly grouped at 93.30–94.17%.

For each 15-second sample, the external share is

$$
s_{\mathrm{external}}(t)=
\frac{r_{\mathrm{external}}(t)}
{r_{\mathrm{external}}(t)+r_{\mathrm{GPU\ hit}}(t)+r_{\mathrm{compute}}(t)}.
$$

## CephFS: active, but unable to drain stores

CephFS did receive traffic. The 3 TiB PVC was freshly created and kubelet eventually reported **206,577,860,608 bytes = 192.39 GiB** used. There were no pod restarts, no OOMs, no `No space left`, no short reads/writes, no permission failures, and no block-I/O exceptions. The two client `ServerDisconnectedError`s occurred during profiling, but they are a consequence-level symptom, not the dominant mechanism.

The failure is in the vLLM tiering backpressure path:

1. The [vLLM v0.23 scheduler](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/distributed/kv_transfer/kv_connector/v1/offloading/scheduler.py#L796-L803) prints `cannot store blocks` only when `manager.prepare_store(...)` returns `None`.
2. The [CPU primary manager](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/v1/kv_offload/cpu/manager.py#L151-L177) returns `None` when it needs space but cannot evict enough blocks.
3. In the [tiering manager](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/v1/kv_offload/tiering/manager.py#L490-L536), a completed GPU-to-CPU store is cascaded to every secondary tier; `primary.prepare_read()` increments the CPU block reference count, pinning that block until the asynchronous secondary job completes.
4. The [filesystem tier](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/v1/kv_offload/tiering/fs/manager.py) writes one block file per key through a dual-queue thread pool. Slow or backlogged CephFS writes therefore leave too many CPU blocks referenced and non-evictable.

The backlog condition can be expressed as

$$
\frac{dB}{dt}=R_{\mathrm{store\ submitted}}-R_{\mathrm{store\ completed}}.
$$

When $dB/dt>0$ for long enough, in-flight secondary writes pin the finite primary CPU tier. At 12.31 minutes this run crossed that point. The warning count is a scheduler retry count, not 102,325 unique failed blocks: 812 request IDs were affected and one request was retried 5,012 times.

The scheduler gauges show the consequence: CephFS averaged **22.84 waiting requests** versus **17.27** for CPU-only and reached 51 versus 44. It also carried more effective prefill concurrency (23.13 versus 17.48), consistent with recomputation replacing reusable external loads.

Figure 6 supplies the strongest temporal corroboration. Before the first store refusal, CephFS averaged **2.11 GiB/s CPU→GPU** and **0.104 million external prompt tokens/s** (five-minute rate representation). After onset, CPU→GPU bandwidth fell by about **66%**, external prompt rate fell by **67.7%**, and local compute rose 4.0×. The CPU-only run shows a much smaller late-run drift, so workload phase alone does not explain the Ceph collapse.

Provenance: vLLM native offload byte counters transformed to five-minute rates and sampled every 15 seconds. These counters cover GPU↔CPU transfers; they do not identify CPU↔filesystem bytes.

## Telemetry gaps

- GPU SM utilization, VRAM used/free, and PCIe RX/TX queries returned **zero series** for all runs. GPU KV-cache occupancy is available and is not a substitute for SM utilization.
- Ceph pool bytes/s, pool IOPS, MDS client operations, MDS memory, OSD latency, and Ceph health queries returned **zero series**. PVC capacity/usage is the only direct Ceph-backed volume signal.
- vLLM exposes GPU↔CPU offload counters but no per-secondary-tier hit, byte, latency, queue-depth, or in-flight-block metrics in these artifacts. Exact CephFS read hits therefore cannot be counted.
- `prefix_cache_hit_rate` archived as zero throughout, while prompt-token-source counters and AIPerf theoretical reuse were non-zero. It is not used for conclusions.

## Acceptance decisions

### No offload versus CPU64 — accept directionally

The configuration difference is isolated, the connector is active, external token sourcing jumps from 0% to 77%, and every client metric improves by roughly 40–103%. The fixed-duration workload and tail censoring prevent a precise confidence interval, but not the direction of the result.

### CPU64+NVMe — accept directionally, repeat under exact controls

CPU capacity is now matched and NVMe traffic is real: 459.8 GiB read, 381.5 GiB written, 13.5% mean busy, zero request errors, and zero `cannot store blocks`. The 10.5% request-throughput, 29.8% TTFT, 22.2% E2E, and 7.3% completed-session improvements are credible directional evidence. Do not call them isolated NVMe effect sizes until `/dev/shm`, path cleanliness, hash seed, and repetitions are controlled.

### CPU64+CephFS — reject as a healthy performance cell

The run proves CephFS writes happened and exposes a repeatable capacity/drain failure. It does not measure sustainable CephFS offload performance after minute 12.31. Preserve it as a failure experiment and use its warning onset as the acceptance gate for the next run.

## Next experiment

1. **Repeat the corrected CPU64 pair under exact controls:** CPU64 and CPU64+NVMe with the same 200 GiB `/dev/shm`, release topology, U=0.55, C=32, TP=2, duration, and image digest.
2. **Clean every secondary tier and fix hashing:** use a run-scoped empty NVMe directory (or explicit pre-run deletion) and `PYTHONHASHSEED=0`; record clean-state proof. Run at least three paired seeds.
3. **Make the Ceph acceptance gate mechanical:** zero `cannot store blocks`; no sustained growth in filesystem store queue; steady external-token share; direct secondary read/write counters present. Increasing CPU to 96 or 128 GiB may buffer bursts, but it is not a fix unless the secondary completion rate catches the submission rate.
4. **Instrument the missing layer:** per-tier lookup hits/misses, bytes submitted/completed, transfer latency, queue depth, in-flight jobs/blocks, and store failures. Add pod-level Ceph client I/O or working Ceph daemon queries. Without these, “CephFS hit count” remains unknowable.
5. **Test CephFS drain capacity:** sweep filesystem `n_write_threads` (default 16), measure completion throughput, and consider reducing file-per-block metadata pressure. Increase threads carefully; the goal is a stable completion rate, not merely a later failure.
6. **Keep AgentX for end-to-end relevance, add a mechanism control:** run at least three seeds per cell and report intervals. Pair that with a fixed request/reuse replay so each tier sees the same prompts. Use total token throughput and prompt-source composition alongside request throughput.

Do **not** raise concurrency yet. This C=32 run already kept the GPU KV cache near full and exposed Ceph backpressure. Do **not** lower GPU memory utilization further until Ceph store draining is fixed; U=0.55 already creates the intended offload pressure.

## Bottom line

The corrected experiment shows a large CPU-offload benefit and a promising capacity-matched NVMe increment: NVMe readback is substantial, the device is not saturated, request and session outcomes improve, and external reuse stays high. Shared-memory, dirty-path, hashing, and replication controls keep the exact NVMe effect provisional. CephFS still fails differently: asynchronous stores pin CPU blocks, CPU eviction fails, external reuse collapses, and recomputation returns. That is storage-tier backpressure—not GPU underutilization, EPP routing, or a need for more concurrency.
