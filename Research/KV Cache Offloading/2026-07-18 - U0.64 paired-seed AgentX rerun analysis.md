## Breakthrough: the cache-source staircase matches the performance staircase

| Precise variant | HBM/local hit | External KV transfer | Recomputed | Total reused |
|---|---:|---:|---:|---:|
| No offload | 42.12% | 0% | 57.88% | 42.12% |
| CPU32 | 44.30% | 22.35% | 33.35% | 66.65% |
| CPU32 + NVMe | 53.87% | 35.01% | 11.12% | 88.88% |

CPU eliminates **24.53 percentage points** of recomputation. NVMe eliminates another **22.23 points**. This is almost the ideal tier separation for the experiment and approaches the trace's approximately 94.8% theoretical cache opportunity.

The workload, U=0.64, and CPU32 are therefore already correctly sized. There is no need to lower HBM, change CPU bytes, or raise concurrency to create a larger gap.

## Breakthrough: the clean no-offload control isolates the crashes to vLLM offloading

Precise no offload completed with:

- 9,884 successful requests;
- zero AIPerf errors;
- zero model restarts;
- zero preemptions;
- zero model memory failures;
- zero CPU throttling.

CPU32 differs from this control only by the vLLM `OffloadingConnector` argument and suffered four worker deaths. CPU+NVMe uses the same offloading framework and suffered two deaths in one worker.

This rules out the following as the primary crash cause:

- AgentX workload shape or seed 42;
- concurrency 128;
- precise EPP by itself;
- the two-node/four-pods-per-node topology;
- HBM pressure;
- host-memory failures;
- CPU throttling;
- NVMe hardware, because CPU-only also crashes.

The common failure boundary is vLLM 0.23.0's offloading path with Qwen3.6's hybrid Mamba/full-attention cache. NVMe is not required to trigger it.

The exact fatal exception is still unavailable because the collector did not save `kubectl logs --previous` for restarted containers. The offload localization is now strong; the exact function remains unknown.

## Configuration bug: requested vLLM 0.24.0 did not deploy

Every `run-plan.json` requests:

```yaml
image: vllm/vllm-openai:v0.24.0
```

Every rendered Deployment contains:

```yaml
image: vllm/vllm-openai:v0.23.0
```

Every model log also reports engine version 0.23.0.

Root cause in Benchflow `src/benchflow/deploy/llmd.py` around lines 1420–1426:

```python
images = kustomization.setdefault("images", [])
if images:
    image = images[0]
    if plan.deployment.runtime.image:
        ...
```

The llm-d v0.8 precise guide's top-level Kustomization has no `images` entries because the vLLM image transformer lives inside the `gpu-vllm` component. Benchflow creates an empty top-level list and then skips the override because `if images` is false. The llm-d component retains v0.23.0.

This means the batch did not test the requested v0.24.0 fixes. The parity of these results is preserved—all variants actually used 0.23.0—but the reliability rerun must fix this renderer bug and assert the final rendered image.

Recommended renderer behavior: when `runtime.image` is set and the top-level list is empty, append an override for the placeholder image name used by the llm-d component, rather than silently doing nothing. Add a test for component-owned image transformers and fail deployment if the final rendered image does not match the resolved run plan.

All 20 no-offload renderer deadlines occur in a tight burst approximately five seconds after profiling starts. Add an explicit load warmup or increase render capacity so the measured window begins only after renderers are hot.

The no-offload run proves these EPP warnings do not crash the model workers. They still degrade precise-routing quality. In particular, the 3,814 parent-key failures in NVMe cause v0.9.0 to drop complete `BlockStored` events from the index.

EPP v0.9.0 defaults only define GPU weight 1.0 and CPU weight 0.8. Unknown tier labels use weight 1.0. Confirm the tier label emitted by vLLM before configuring an explicit GPU > CPU > filesystem cost hierarchy.

## Approximate versus precise observation

The optimized approximate baseline and clean precise no-offload run have nearly identical throughput and E2E:

- RPS: 5.372 approximate versus 5.417 precise;
- average E2E: 11,391 ms versus 11,314 ms;
- output token throughput: 3,611 versus 3,643.

Precise no-offload TTFT is worse:

- average: 1,720 ms versus 1,375 ms;
- p95: 4,509 ms versus 3,517 ms.

Prompt local-hit share is also slightly lower: 42.12% precise versus 44.33% approximate.

This means precise routing is not yet producing an HBM-only benefit on top of the approximate scorer. Likely contributors are per-request rendering/tokenization overhead, missing prefix data for about 2.8% of requests, early render timeouts, dropped parent events, coarse 1,088-token aligned blocks, and an AgentX reuse pattern that approximate routing already handles reasonably well. This does not invalidate the precise offload comparison because all three tier variants share the same precise topology.

## Decisions

- Keep `gpu-memory-utilization=0.64`. It already creates excellent tier separation without preemption.
- Keep CPU at 32 GiB. It creates the desired midpoint rather than absorbing the NVMe reuse tail.
- Keep concurrency 128 for the reliability rerun.
- Keep seed 42 until one zero-error triplet is achieved. Then run three to five paired seeds.
- Do not tune NVMe threads or hardware; it has ample headroom.
- Fix the Benchflow image override and actually deploy vLLM 0.24.0 or a selected newer commit with relevant hybrid/HMA/offload fixes.
- Preserve `kubectl logs --previous` before any pod is deleted.
- Repair or upgrade EPP parent-event handling and verify tier weights.
- Warm or scale renderers before profiling.
- Restore DCGM queries; all runs still lack GPU utilization/memory telemetry.

## Working conclusion

The experimental scenario is now correctly sized and produces the desired performance gaps: CPU gives one strong step and NVMe gives another. The workload is not the problem, and NVMe is not the problem.

The blocker is that the offload variants ran an unintended vLLM 0.23.0 image and suffered EngineCore deaths. Precise no offload is clean, isolating the failure to the common offloading path. Fix the Benchflow image override, deploy the intended newer vLLM, capture previous logs, and rerun without changing U=0.64, CPU32, concurrency 128, or seed 42.
