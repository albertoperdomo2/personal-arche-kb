## Controlled settings confirmed

All three available runs used:

- the same AgentX WEKA trace and data profile;
- duration 1,800 seconds;
- offered concurrency 128;
- `random_seed=42`;
- eight replicas at TP2, placed four per node on the same two H100 nodes;
- Qwen3.6-35B-A3B;
- vLLM 0.23.0;
- `gpu-memory-utilization=0.64`;
- maximum model length 131,072;
- prefix caching enabled;
- aligned cache block size 1,088 for the hybrid Mamba/attention model;
- 1,160 GPU cache blocks, or approximately 1.197 million logical GPU-cache tokens per replica.

The CPU tier was `34359738368` bytes, 32 GiB per vLLM engine/replica, in both offload variants. The NVMe variant added the filesystem secondary tier at `/mnt/nvme-kv-cache`.

The optimized baseline still differs architecturally: it uses the approximate prefix-cache scorer with one EPP, while the CPU variants use the precise producer with two EPP replicas and three tokenizer/render replicas. Baseline-to-CPU therefore conflates routing mode and offloading. The pending precise no-offload result is required for the primary three-way comparison.

| CPU32 | 10,845 | 5.928 | 1,213 ms | 681 ms | 3,510 ms | 8,824 ms | 29,317 ms | 3,980 | 48 |
| CPU32 + NVMe | 11,891 | 6.499 | 797 ms | 582 ms | 1,918 ms | 6,822 ms | 23,044 ms | 4,421 | 15 |

Observed deltas:

- CPU versus optimized baseline: +10.3% RPS, -11.8% average TTFT, -22.5% average E2E.
- NVMe versus CPU: +9.6% RPS, -34.3% average TTFT, -45.4% p95 TTFT, -22.7% average E2E.
- NVMe versus optimized baseline: +21.0% RPS, -42.0% average TTFT, -40.1% average E2E.

These are meaningful gains, particularly the NVMe tail-latency improvement. They cannot be treated as publication-quality effect sizes because CPU lost four workers while NVMe lost one worker twice.

## Breakthrough: prompt-token accounting proves that both tiers worked

The vLLM prompt-token source metrics explain the latency changes:

| Variant | HBM/local hit | External KV transfer | Recomputed | Total reused |
|---|---:|---:|---:|---:|
| Optimized baseline | 44.33% | 0% | 55.67% | 44.33% |
| CPU32 | 44.30% | 22.35% | 33.35% | 66.65% |
| CPU32 + NVMe | 53.87% | 35.01% | 11.12% | 88.88% |

CPU eliminated about 22.3 percentage points of prompt recomputation. Adding NVMe eliminated another 22.2 points. The achieved 88.9% total reuse approaches the trace's approximately 94.8% theoretical cache-hit opportunity. This is the direct performance mechanism; the gains are not a random-seed artifact.

## Breakthrough: the workload was not saturating compute, HBM capacity, CPU, memory, or storage

| Baseline | 39.6% / 71.0% / 95.5% | 58.2 / 74.1 | 1.83 / 5.05 / 13 | approximately 3.75 |

| CPU32 + NVMe | 28.2% / 48.1% / 66.4% | 40.0 / 54.1 | 1.25 / 4.0 / 6 | 0 |

The faster variants carry fewer concurrent in-flight requests in this closed-loop trace, so their GPU-cache utilization and effective concurrency fall. Queueing is low. CPU throttling is negligible and model-container memory-failure counters are zero.

### Offload activity

CPU32 cluster transfer averages:

- CPU to GPU: 1.63 GB/s, approximately 2.94 TB over the run;
- GPU to CPU: 3.26 GB/s, approximately 5.87 TB over the run.

CPU32 + NVMe cluster transfer averages:

- CPU to GPU: 2.85 GB/s, approximately 5.14 TB;
- GPU to CPU: 1.21 GB/s, approximately 2.18 TB;
- NVMe reads: 2.57 GB/s, approximately 4.63 TB;
- NVMe writes: 1.31 GB/s, approximately 2.36 TB.

The two NVMe devices averaged 34.3% and 40.2% busy, with maxima below 47%. Filesystem occupancy ended near 17.5%. NVMe was active and had substantial headroom; it was not the bottleneck.

## Failure diagnosis

The AIPerf errors are consequences of model EngineCore deaths, not evidence that concurrency 128 saturated the service.

### CPU32

- 48 failed requests out of 10,893 attempts: 0.441%.
- Four one-second error bursts align exactly with four different model pods exiting and restarting.
- Each restarted backend took approximately 2 minutes 40 seconds to return to routing.
- Kubernetes recorded `Completed`, exit code 0, rather than `OOMKilled`.
- Memory-failure counters were zero and there was no material CPU throttling.

### CPU32 + NVMe

- 15 failed requests out of 11,906 attempts: 0.126%.
- One model pod died twice.
- That single backend was effectively unavailable for approximately 6 minutes 39 seconds.
- Kubernetes again recorded clean exit code 0 rather than an OOM.

vLLM's API process can terminate cleanly after its EngineCore child has already failed, so exit code 0 does not make the event benign.

### Exact fatal exception is missing

The artifact collector saved only the current container log. For every restarted pod, the current log begins after the crash. It did not collect `kubectl logs --previous`, so the fatal EngineCore traceback referenced by the AIPerf error is absent.

Therefore the exact failing function cannot be proved from this batch. The strongest current localization is the experimental vLLM cache path:

- Qwen3.6 resolves to a hybrid Mamba/full-attention architecture;
- vLLM logs call Mamba prefix caching in `align` mode experimental;
- vLLM logs call `OffloadingSpec` experimental;
- only the two available offload variants show EngineCore deaths;
- there is no evidence of GPU OOM, host-memory failure, CPU starvation, request saturation, or NVMe saturation.

This is a suspected vLLM 0.23.0 hybrid-prefix/offload defect, not yet an exact root cause. The pending precise no-offload run and the previous-container traceback are required to separate precise-prefix handling from offloading.

## Precise-router health findings

The deployed llm-d EPP/kv-cache version is v0.9.0. During each 30-minute precise run:

| EPP symptom | CPU32 | CPU32 + NVMe | Impact |
|---|---:|---:|---|
| `PrefixCacheMatchInfo not found for endpoint` | 2,348 log entries / 306 requests | 2,646 / 339 requests | Prefix score becomes zero for affected endpoints/requests |
| Renderer/tokenization deadlines | 9 requests | 22 requests | Precise score falls back for those requests |
| `Failed to get request key for parent block` | 171 | 3,814 | Entire block-store events are dropped from the precise index |
| SSE `invalid character '#'` parser noise | 5,400 | 5,399 | Likely keepalive/comment parsing; nearly identical across variants |

The parent-key failure is especially important. The v0.9.0 pool logs the error and executes `continue`, dropping that `BlockStored` event. The 22-fold increase in the NVMe run means its multi-tier event stream is materially less complete in EPP's precise index. This can leave some filesystem-resident reuse unrecognized by routing even while the local vLLM offloader still serves the data.

v0.9.0 defaults precise-tier weights to GPU 1.0 and CPU 0.8. There is no default filesystem tier. Unknown device-tier names fall back to weight 1.0. The deployment did not set `kvCacheBackendConfigs`. Before choosing an FS weight, capture the actual device-tier value emitted by vLLM 0.23.0; then configure GPU > CPU > filesystem and verify that this exact router build supports the field. Do not blindly add `fs` until the event label is confirmed.

The response-parser noise and prefix-match gaps should also be removed before final measurement, but their nearly equal frequency does not explain the CPU-to-NVMe performance gap.

## Decisions

### Do not increase GPU-memory utilization

Higher GPU allocation increases HBM KV reach and hides CPU/NVMe benefits. It also does not address these clean EngineCore exits, which have no OOM signature. Keep `0.64` for the immediate diagnostic rerun.

After the stack is stable, if a larger tier gap is still required, try `0.62` and then `0.60`, with rejection gates for preemption and queueing. Do not lower HBM while the crash is still unobservable.

### Do not change seed as a fix

All three runs already used seed 42. A different seed may avoid a trace item that triggers the defect, but that would hide rather than fix it. Once stable, run three to five paired seeds and randomize variant order.

### Do not increase concurrency yet

Concurrency 128 already drove 22–35% of prompt tokens through the external KV path and multiple terabytes through CPU/NVMe. Queueing and cache pressure do not show an underloaded offload experiment. More concurrency before reliability is fixed would add a confounder and likely increase the number of affected requests when a worker dies.

## Next controlled procedure

### 1. Fix artifact collection before the next long run

For every model and EPP container, save:

- current logs;
- `kubectl logs --previous` when restart count is nonzero;
- pod termination reason, signal, exit code, start/finish timestamps, and termination message;
- namespace events sorted by timestamp;
- vLLM EngineCore logs and Python traceback;
- DCGM GPU utilization/memory metrics;
- EPP precise-index error counts.

A run with a restart but no previous log is diagnostically incomplete.

### 2. Run a short isolation matrix first

Use the same deployment, seed 42, concurrency 128, and 10-minute duration:

1. precise, no offload;
2. precise + CPU32;
3. precise + CPU32 + NVMe.

If only offload variants die, run one short offload test with precise EPP disabled/approximate routing. That separates the vLLM offloader from the EPP event subscriber. If necessary, use a full-attention model as a second isolation control for the hybrid-Mamba path.

### 3. Repair or upgrade EPP index handling

Before a final 30-minute batch:

- eliminate `Failed to get request key for parent block`, especially for multi-tier events;
- confirm the exact vLLM event-tier names and configure explicit cost weights;
- eliminate persistent `PrefixCacheMatchInfo not found`;
- scale or warm renderers until tokenization deadlines are zero;
- test a router build newer than deployed v0.9.0 if it contains the relevant tier/event fixes;
- verify response parsing no longer treats SSE comment lines as JSON.

### 4. Repeat the clean primary experiment

Compare only:

1. precise, no offload;
2. precise + CPU32;
3. precise + CPU32 + NVMe.

Hold topology, images, EPP/render count, cache cleaning, `U=0.64`, concurrency 128, and seed constant. Repeat across three paired seeds after one clean seed-42 triplet.

### Acceptance gates

Reject a run if any of the following occurs:

- any model/EPP restart;
- any EngineCore HTTP 500;
- nonzero previous-container fatal traceback;
- request error rate above 0.1% (prefer zero);
- any preemption in an offload variant;
- missing GPU metrics;
- any model replica absent during measurement;
- renderer timeouts after warmup;
- persistent missing prefix-match information;
- parent-key/index drops materially above zero;
- NVMe busy above 80–85% or filesystem free space below 20%.

## Working conclusion

The rerun validates the cache-offload mechanism more strongly than the initial experiments: CPU reduced prompt recomputation and NVMe reduced it again, yielding large TTFT and E2E improvements. NVMe performance, GPU capacity pressure, concurrency, and random seed are not the present limitation.

The immediate blocker is reliability and observability: the offload runs suffered EngineCore deaths whose previous logs were not collected, and the precise EPP dropped thousands of multi-tier block events. Keep `U=0.64`, CPU32, concurrency 128, and seed 42 while isolating those defects. Only after a zero-restart clean triplet should HBM be lowered to 0.62/0.60 or concurrency be swept.
