# 2026-07-25 — Qwen3.6 35B-A3B AgentX standardized offload matrix (batch 2)

## Executive summary

This is a four-cell, standardized comparison of HBM-only, 64 GiB CPU tier, 64 GiB CPU plus local NVMe, and 64 GiB CPU plus tuned CephFS. All cells use the same Qwen3.6-35B-A3B FP8 deployment, TP=4 on four H100s, `gpu-memory-utilization=0.85`, 131,072-token context, 200 GiB `/dev/shm`, AgentX/WEKA workload, seed 42, and a 1,800-second profiling window.

The secondary tiers improve this workload substantially: CPU-only reaches 1.423 requests/s, NVMe 1.508 requests/s, and CephFS 1.517 requests/s versus 1.092 requests/s HBM-only. Mean E2E falls from 31.19 s to 16.19 s, 13.20 s, and 13.20 s respectively. Unlike the earlier low-pressure batch, mean KV occupancy is 35–50%, and external KV transfer is material (28–34%) in the offload cells.

|---|---|---|---|---:|---|
| No offload | HBM only | none | 200 GiB | 0 | 0 / 0 |
| CPU 64 GiB | TieringOffloadingSpec, 64 GiB CPU | none | 200 GiB | 0 | 0 / 0 |
| CPU 64 GiB + NVMe | TieringOffloadingSpec, 64 GiB CPU | hostPath NVMe `/mnt/nvme-kv-cache` | 200 GiB | 0 | 0 / 0 |
| CPU 64 GiB + CephFS | TieringOffloadingSpec, 64 GiB CPU | PVC `vllm-kv-cache`, tuned read/write threads | 200 GiB | 0 | 0 / 0 |

The resource evidence shows a materially pressured workload: mean KV occupancy is 49.8% HBM-only, 38.8% CPU-only, 35.0% NVMe, and 34.8% CephFS; HBM-only peaks at 87.8%. External KV transfer rises from 0% HBM-only to 28.2% CPU-only, 33.8% NVMe, and 34.2% CephFS. NVMe averaged 387 MB/s reads and 262 MB/s writes; CephFS PVC occupancy averaged 5.1%. No CephFS pool/MDS throughput counters were exported.

## Interpretation and hypotheses

1. **The workload is not forcing a large offload working set.** This run is much better sized for offload study: HBM-only reaches 87.8% KV occupancy and the tiered cells source roughly one-third of prompt tokens externally. The workload is therefore exercising the tier path rather than merely provisioning it.
2. **The CPU tier alone is not the bottleneck or benefit source here.** CPU64 improves throughput by 30.4% versus HBM-only and cuts mean E2E by 48.1%; the HBM-only cell is clearly under pressure while the CPU tier relieves KV residency pressure.
3. **NVMe is strong, but CephFS is marginally faster in this run; the evidence does not prove storage bandwidth alone is causal.** NVMe has the highest measured throughput and lowest latency, but the gain could combine reduced eviction/reload stalls, scheduling variance, and the small extra external-transfer share. Use matched repeated seeds and add per-tier read/write latency and cache-hit/miss counters before attributing causality to raw device bandwidth.
4. **Tuned CephFS is close to NVMe, not catastrophically slower.** Its 1.442 req/s is 0.9% below NVMe and its mean E2E is 0.52 s higher. The available PVC metric confirms storage use, but missing CephFS pool/MDS operation series limits a direct filesystem-throughput conclusion.
5. **The run completed cleanly.** There are no model-pod restarts, server tracebacks, or CUDA OOMs; however, HBM-only has 1 request error and NVMe/CephFS have 2 each, so request-level error artifacts should be inspected before final claims. Cutoff-incomplete sessions are a workload-window artifact, not failures.

## Recommended next experiment

Hold the deployment and `/dev/shm` constant, increase concurrency in steps (32, 64, 128, 256), and collect at least three repetitions per cell. Stop or mark the point when KV occupancy reaches the desired pressure band (for example 70–90% rather than 10%). Export NVMe device latency/queue depth and CephFS client read/write/MDS counters at the same 15-second cadence. This separates workload sizing from storage-medium effects and turns the current directional result into a causal offload curve.
