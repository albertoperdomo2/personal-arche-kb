Why do the vLLM 0.24.0 precise+CPU and precise+CPU+NVMe AgentX runs have hundreds of failed requests while the approximate and precise no-offload controls have none? Is this workload saturation, model-worker instability, CPU/NVMe performance, or the routing path?

## Controlled parity and image verification

All variants used:

- AgentX WEKA trace `semianalysisai/cc-traces-weka-with-subagents-060826`;
- concurrency 128, seed 42, and 1,800-second profiling;
- eight TP2 replicas on the same two H100 nodes;
- `gpu-memory-utilization=0.64`;
- Qwen3.6-35B-A3B and max model length 131,072;
- EPP image `ghcr.io/llm-d/llm-d-router-endpoint-picker:v0.9.0`.

Run plan, rendered Deployment, pod manifest, and model startup logs all agree on `vllm/vllm-openai:v0.24.0`. The previous Benchflow runtime-image override problem is fixed.

The two offload variants both use 32 GiB CPU per replica. The NVMe variant adds `TieringOffloadingSpec` and the local filesystem tier.

## Breakthrough: request failures are EPP deaths, not model deaths

All 16 model workers in the two offload variants have restart count zero and no fatal traceback. In contrast, all four EPP containers (two per offload run) ended in:

```text
State:          Waiting
Reason:         CrashLoopBackOff
Last State:     Terminated
Reason:         Error
Exit Code:      2
Restart Count:  10
```

The EPP logs end with the same panic:

```text
panic: runtime error: index out of range [0] with length 0

github.com/llm-d/llm-d-kv-cache/pkg/kvcache/kvblock.(*InMemoryIndex).Add
github.com/llm-d/llm-d-kv-cache/pkg/kvevents.(*Pool).processEventBatch
```

## Exact root cause

In `llm-d-kv-cache@v0.9.0`, `Pool.processEventBatch` handles an offloading `BlockStored` event whose `BlockHashes` list is empty but whose tokens produce one request key.

It constructs the engine-key slice with:

```go
engineKeys := make([]kvblock.BlockHash, len(ev.BlockHashes))
```

For zero hashes this is a non-nil, zero-length slice. `InMemoryIndex.Add` in v0.9.0 checks only:

```go
if engineKeys != nil {
    ...
    ek := engineKeys[i*len(engineKeys)/n]
}
```

With zero engine keys and one request key, it indexes `engineKeys[0]` and panics.

This missing guard was fixed after v0.9.0 by llm-d-kv-cache PR [#670](https://github.com/llm-d/llm-d-kv-cache/pull/670), commit `c4e7265938985c455b177940815a99491f218ff6`. Current llm-d-router source uses a shared helper that returns early when either key slice is empty, and includes `TestEngineToRequestMapping_EmptySlices`.

The v0.9.0 release predates this fix. Its release notes only track filesystem-backend migration through vLLM 0.23.0.

## Client-visible failure chain

1. An offloading KV event triggers the empty-slice panic.
2. EPP exits with code 2.
3. Envoy loses the external-processing stream.
4. Existing chunked inference responses terminate midstream and AIPerf records `ClientPayloadError` / `TransferEncodingError`.
5. Requests arriving during EPP downtime receive empty HTTP 500 responses; the NVMe run also records one 503.
6. Kubernetes restarts EPP; it consumes another triggering event and crashes again.
7. Each restart erases the in-memory precise-prefix index, producing many follow-on `engine key not found` and missing-prefix-score messages.

Timing proves the chain:

- CPU: an EPP exited at 12:27:46; 39 active streams failed together at 12:27:47.
- CPU+NVMe: one EPP exited at 13:18:57; 18 streams failed at 13:18:58.
- CPU+NVMe: the other exited at 13:19:11; 18 streams failed at 13:19:12.

Error breakdown:

|---|---:|---:|---:|---:|
| CPU32 | 469 | 260 | 0 | 729 |
| CPU32+NVMe | 379 | 319 | 1 | 699 |

## Why saturation and NVMe are ruled out

- Model restart count: zero in both offload variants.
- Model memory failure rate: zero.
- Model CPU throttling: zero.
- EPP termination is a Go panic/exit 2, not OOMKilled/137 or a liveness kill.
- CPU capacity waiting p95 is about 6; CPU+NVMe capacity waiting is zero, with p95 deferred waiting about 11.
- Mean GPU KV usage is about 42% for CPU and 26% for CPU+NVMe, not pinned at 100%.
- NVMe was active: approximately 8.17 GB/s aggregate reads and 1.45 GB/s writes; node devices averaged about 78% and 81% busy.

Concurrency 128 increases how many streams are lost per restart, but lowering concurrency cannot fix the panic. CPU-only triggers the same defect, so NVMe is not required.

## Other findings

The recurring EPP response parser message `invalid character '#' looking for beginning of value` is not the request-failure root cause. It appears by the thousands in successful control runs, after which EPP forwards the response. It remains a noisy SSE-comment parsing issue to fix separately.

AIPerf's thousands of "counter reset" warnings should not be interpreted as thousands of model restarts. The pod state and model logs show none; those warnings result from how same-labeled per-pod counters are combined by its server-metrics exporter.

## Decisions

- Reject the CPU and CPU+NVMe results for performance comparison. Successful-only latency/throughput are biased by dropped work, EPP downtime, and repeated precise-index loss.
- Do not change GPU utilization, CPU size, concurrency, seed, or NVMe tuning yet.
- First replace EPP v0.9.0 with an image built after commit `c4e7265938985c455b177940815a99491f218ff6`.
- `ghcr.io/llm-d/llm-d-router-endpoint-picker:main` is suitable for a smoke test but is mutable. Publish/select an immutable commit or release image and pin its digest for final benchmarks.
- In Benchflow, set the EPP override at `spec.overrides.images.scheduler`.
- Add a pre-profile reliability gate: all EPP/model replicas Ready; restart delta zero after warmup; reject immediately on any panic or request error.
- Run a 5–10 minute CPU32 test first, then CPU32+NVMe, then the full paired four-way batch unchanged.

## Validation criteria

A run is acceptable only if:

- requested, rendered, pod, and startup-log versions agree;
- EPP and model restart deltas remain zero after warmup;
- no `InMemoryIndex.Add` panic appears;
- AIPerf records zero HTTP 500/503 and zero truncated streams;
- precise-prefix parent/index errors do not surge after startup.

After a clean paired batch, resume three-to-five paired seeds and performance analysis.
