# vLLM 0.24 + fixed-EPP AgentX rerun analysis

Date: 2026-07-19  
Experiment: Qwen3.6-35B-A3B, 8 replicas, TP=2, `gpu_memory_utilization=0.64`, 30-minute AIPerf AgentX run at concurrency 128 and seed 42.

## Executive conclusion

This is the first four-way batch in this series that is usable for performance analysis. The new EPP image fixes the prior offload-triggered CrashLoop: every EPP and model pod stayed Ready with restart count zero, and there are no panics or model-server errors.

The result is a real performance staircase, but most of the gain is delivered by the first offload tier:

- precise routing versus optimized approximate routing: **+2.74% request throughput**;
- CPU32 versus precise no-offload: **+16.36% request throughput**, **-52.47% mean TTFT**, and **-32.09% mean request latency**;
- CPU32+NVMe versus CPU32: only **+0.26% request throughput**, but **-6.04% mean TTFT**, **-24.29% p95 TTFT**, and **-5.08% mean request latency**.

NVMe is not idle and the SSDs are not the measured bottleneck. The NVMe run read about 2.05 TB and wrote 2.04 TB during the profiling window, at approximately 1.14 GB/s in each direction. Device busy time averaged only 24–29% per node and peaked below 35%. NVMe reduces locally computed prompt tokens from 14.29% with CPU32 to 9.35%, but the workload then spends most of its critical path on decode and agent orchestration. This is why NVMe improves latency tails without materially increasing completed requests per second.

Two non-storage issues still limit the experiment:

1. Precise routing synchronously tokenizes each long chat request through three CPU render pods. EPP dispatch is about 139–149 ms p50 in the precise variants versus 10.6 ms in approximate, with 4–5 second p99/max outliers and 21–26 render timeouts per run.
2. Only the NVMe run logs 1,116 `Failed to get request key for parent block` errors across 319 unique parent engine keys. The current router code skips the corresponding `BlockStored` event when this happens, so EPP's precise view of NVMe-resident blocks is incomplete. This does not cause request failures, but it can suppress the incremental benefit of tiered storage and should be fixed before calling the CPU-versus-NVMe result final.

## Why precise routing alone has a small gain

The workload's theoretical shared-prefix potential is almost identical in all four runs (94.74–94.80%), and mean input length is tightly matched (62.1–62.4k tokens). Precise routing raises the measured GPU-local prompt hit share by only 4.23 percentage points over optimized approximate routing. The approximate scorer is already effective for this corpus and topology.

At the same time, precise EPP has a synchronous real-tokenization cost. Matching `EPP received request` and `EPP sent request body response(s) to proxy` timestamps gives:

This dispatch tax is large enough to explain why precise no-offload has a 9.66% worse mean TTFT than approximate even though its E2E latency is 8.17% better. It is common to all precise variants, so it does not explain the small CPU-to-NVMe throughput delta.

The precise logs contain 21, 24, and 26 `tokenization failed ... context deadline exceeded` messages. The render service is dedicated, but only three pods are deployed and each is guaranteed one CPU while tokenizing roughly 62k-token prompts. Calls are also unevenly distributed among render pods. Render CPU utilization and request-latency telemetry are missing from these artifacts, so CPU saturation is not directly proven; the five-second outliers and timeout messages prove the service is undersized or insufficiently balanced for this request shape.

For the NVMe run specifically:

- reads: 1.139 GB/s average, 1.530 GB/s maximum, about 2.051 TB total;
- writes: 1.134 GB/s average, 2.043 GB/s maximum, about 2.042 TB total;
- IOPS: 887 reads/s and 1,091 writes/s average, implying large roughly 1.28 MB reads and 1.04 MB writes rather than a small-random-I/O pattern;
- device busy: 28.5% mean / 34.6% max on one node and 23.7% mean / 30.6% max on the other;
- filesystem usage grew into roughly the 15% range and did not approach capacity.

This rules out “NVMe received no traffic” and argues strongly against raw SSD bandwidth as the reason for the flat request-throughput result. The artifacts do not include device latency or queue-depth histograms, so they cannot rule out every storage-tail effect, but neither the device-busy metrics nor model logs show a storage saturation or I/O failure signature.

## Saturation and workload-shape assessment

This batch is not failing because queues, memory, or preemption are out of control:

| Metric | Approximate | Precise no-offload | Precise CPU32 | Precise CPU32+NVMe |
|---|---:|---:|---:|---:|
| Mean GPU KV usage | 39.2% | 35.8% | 29.3% | 26.9% |
| p95 GPU KV usage | 70.7% | 57.3% | 51.3% | 50.1% |
| Mean running requests, cluster | 57.9 | 52.9 | 43.0 | 39.8 |
| Mean waiting requests, cluster | 1.90 | 2.09 | 0.23 | 0.52 |
| p95 waiting requests, cluster | 6.0 | 6.05 | 1.05 | 2.05 |
| Estimated preemptions | 0.74 | 0.72 | 1.92 | 0.00 |
| Model memory failures | 0 | 0 | 0 | 0 |
| Model CPU throttling | effectively 0 | 0 | 0 | 0 |

GPU-core utilization data is absent from all four Prometheus exports, so the report cannot claim a measured GPU SM saturation percentage. Nevertheless, the long mean output sequence (667–682 tokens), output throughput plateau around 4.4k tokens/s in the offload variants, low waiting queues, and sharply reduced prompt recomputation show that CPU32 moves the workload away from prefill pressure. NVMe removes another third of the CPU32 recomputation share, but it cannot shorten the large decode component enough to produce another large RPS step.

The nominal concurrency of 128 is not the same as 128 continuously active model requests. AIPerf's agentic dependencies and idle gaps yield effective request concurrency of about 61.1 approximate, 57.7 precise no-offload, 45.6 CPU32, and 43.4 CPU32+NVMe. The offload variants complete work faster and therefore carry fewer simultaneous active requests. This workload is suitable for demonstrating cache benefits, but at this setting it is not a strong stress test of the secondary tier.

## Reliability and remaining correctness signals

- All EPP and model pods: Ready, restart count zero.
- No EPP panic and no model `ERROR`, exception, traceback, OOM, or timeout lines.
- Approximate, CPU32, and CPU32+NVMe each have one HTTP 503: `upstream connect error or disconnect/reset before headers. reset reason: connection termination`. The error rates are 0.008–0.010%. They are isolated, do not coincide with a pod restart, and have no model/EPP failure signature. Treat them as rare gateway/upstream connection transients, not offload failures; gateway logs were not captured, so a more exact attribution is not possible.
- AIPerf reports no context overflows and no requested-output-length mismatches. End-of-duration cancellations are normal timed-profile shutdowns rather than request failures.
- All runs log thousands of non-fatal EPP `parsing response: invalid character '#'` messages. They do not correlate with client errors and appear to be response-parser/metrics noise, but should be fixed before relying on EPP-derived response metrics.
- Precise EPP sometimes cannot prepare match data: 153, 167, and 195 distinct requests respectively have `PrefixCacheMatchInfo not found for endpoint` fallbacks across all eight endpoints. These are a small but measurable source of score-zero routing fallback.
- The NVMe-only missing-parent errors are more serious for benchmark interpretation. In `pkg/kvevents/pool.go`, failure to resolve `ParentHash` executes `continue`, dropping that complete `BlockStored` event from the precise index. The 1,116 log lines represent 319 unique missing parent keys and persist throughout the 30-minute window.

## Recommended next experiment

Do not raise `gpu_memory_utilization` to make NVMe look better. Also do not lower GPU memory first. The current GPU cache setting already produces a clear no-offload-to-CPU gap, and changing it adds a second mechanism to the CPU-versus-NVMe comparison.

The highest-value sequence is:

1. **Fix measurement-path overhead and correctness.** Align the render image to vLLM 0.24.0; give render pods an explicit multi-core request, add render CPU/latency metrics, and scale from three to at least six replicas or use a topology that balances per-request connections. Require zero tokenization timeouts. Fix or instrument the NVMe missing-parent event path so no `BlockStored` event is silently skipped.
2. **Repeat the current point.** Run at least three paired repetitions/seeds. A 0.26% CPU-to-NVMe RPS delta is well within expected run-to-run variance; the 24% p95 TTFT reduction is a stronger candidate effect but still needs replication.
3. **Reduce the primary CPU tier, equally in both offload variants.** Test 16 GiB per replica before changing GPU memory. CPU32 across eight replicas provides 256 GiB of aggregate primary-tier capacity and already avoids 85.7% of prompt computation. CPU16 should make CPU-only evict more reusable blocks while allowing CPU+NVMe to retain them in the secondary tier.
4. **Sweep nominal concurrency.** Use 128, 192, and 256 with CPU16. The target is not failure or a permanently full queue; it is enough active agent state to expand the reuse working set beyond CPU capacity. Watch effective concurrency, p95 waiting requests, local-compute share, external-transfer share, and error rate.
5. **Only then test lower GPU memory.** If CPU16/concurrency 256 still does not separate the tiers, compare `gpu_memory_utilization=0.64` with 0.56 while keeping every other setting paired. Stop lowering it if preemptions, capacity waits, or TTFT regressions dominate.

A useful success condition for a publication-quality CPU-versus-NVMe point is:

- CPU-only local-compute share: roughly 20–35%;
- CPU+NVMe local-compute share: below 10–15%;
- zero EPP/model restarts and effectively zero request errors;
- zero renderer timeouts and zero skipped NVMe parent events;
- NVMe device busy safely below sustained saturation;
- a replicated latency or throughput delta larger than run-to-run variation.

Suggested compact matrix after the two fixes:

| Phase | GPU memory utilization | CPU bytes/replica | Concurrency | Repetitions | Purpose |
|---|---:|---:|---:|---:|---|
| Control | 0.64 | 32 GiB | 128 | 3 | Reproduce this clean point and estimate noise |
| Tier sizing | 0.64 | 16 GiB | 128 | 3 | Increase CPU-versus-NVMe capacity contrast |
| Working-set pressure | 0.64 | 16 GiB | 192, 256 | 3 each | Force more reuse beyond the CPU tier |
| Optional HBM sensitivity | 0.56 | 16 GiB | best prior concurrency | 3 | Test whether smaller HBM widens all offload gaps |

If the goal is specifically a large requests/second gap, retain this AgentX trace as the primary realistic workload and add a secondary cache-sensitive agentic profile with shorter outputs. The current 667–682-token mean output makes decode a large part of every request and naturally limits how much any prompt-cache tier can change end-to-end throughput.
