# 2026-07-23 — Qwen3.6 35B AgentX cleaned TieringOffloadingSpec matrix

## Executive conclusion

These four runs show a **real offload staircase**. CPU 64 GiB is already highly effective, raising request throughput +106.1% over no offload. CPU64+NVMe is fastest and adds +7.8% over CPU64; CPU64+CephFS remains well ahead of no offload but is -40.3% versus CPU64 and -44.6% versus NVMe. CPU capacity and the shared-memory setting are matched across the new offload cells, and all three use the same `TieringOffloadingSpec`. The supplied no-offload baseline is older and has a different node and `/dev/shm`, so baseline deltas are directional; CPU64 versus NVMe versus CephFS is the controlled comparison.

- **No offload:** 0.578 requests/s, 420.1 output tokens/s, mean TTFT 32.968 s, mean E2E 50.511 s, and 26 completed sessions.
- **CPU 64 GiB:** 1.191 requests/s (+106.1% versus no offload), 854.7 output tokens/s, mean TTFT 14.539 s, mean E2E 25.439 s, and 41 completed sessions. External KV supplied 76.61% of prompt tokens. This is a **successful CPU-offload point**.
- **CPU 64 GiB + NVMe:** 1.284 requests/s (+122.2% versus no offload), 924.0 output tokens/s (+120.0%), mean TTFT 10.572 s (-67.9%), mean E2E 20.287 s (-59.8%), and 44 completed sessions.
- **CPU 64 GiB + CephFS:** 0.711 requests/s (+23.0% versus no offload, -44.6% versus NVMe), mean TTFT 20.579 s, mean E2E 32.841 s, and 29 completed sessions. Its retained model-log tail contains at least 66,320 `cannot store blocks` warnings across 271 request IDs.
- All model pods had **zero restarts**, zero preemptions, zero CUDA OOMs, zero missing-parent errors, and zero server tracebacks. Every configuration except CPU64 has one isolated client `ServerDisconnectedError`; that is not the performance mechanism.

The four deployments now hold `/dev/shm`, CPU capacity, TieringOffloadingSpec, model, and workload shape constant across the offload cells. The no-offload baseline is an older U=0.55/C=32 control on the other H100 node, so the cleanest causal comparison is CPU64 versus NVMe versus CephFS; baseline deltas remain directional.

## Controlled workload and deployment audit

The controlled dimensions are strong: all four runs use `Qwen/Qwen3.6-35B-A3B`, one replica, TP=2 on two H100s, `vllm/vllm-openai:v0.23.0` at image digest `sha256:3a1e7f…bdbe3ac0`, nodes `diadochos-hqxzk-gpu-h100-6kl5z` (baseline) and `diadochos-hqxzk-gpu-h100-fx7c8` (offload cells), `gpu-memory-utilization=0.55`, `max-num-seqs=256`, `max-model-len=131072`, prefix caching, AgentX MVP, the same WEKA repository, seed 42, concurrency 32, and a 1,800-second send window. Successful matched requests differ by only 3 prompt tokens at p95 between CPU64 and NVMe, and 3 between NVMe and CephFS. Workload-shape drift does not explain either gap.

The important uncontrolled dimensions are:

| Configuration | Connector implementation | CPU bytes flag | Secondary tier | `/dev/shm` |
|---|---|---:|---|---:|
| No offload | none | — | none | 1 GiB |
| CPU 64 GiB | default `CPUOffloadingSpec` | 64 GiB | none | 1 GiB |
| CPU 64 GiB + NVMe | `TieringOffloadingSpec` | 64 GiB | hostPath filesystem | 200 GiB |
| CPU 64 GiB + CephFS | `TieringOffloadingSpec` | 64 GiB | `vllm-kv-cache` PVC | 128 GiB |

The CPU64, NVMe, and CephFS cells all initialize the same 64 GiB `TieringOffloadingSpec`; their mean working sets are within 0.2 GiB, so host-memory capacity is not the differentiator. Mean model-container working set is 141.3 GiB for CPU64, 141.3 GiB for NVMe, and 141.4 GiB for CephFS, so effective host-memory footprint is closely matched. The remaining CPU-versus-NVMe confound is implementation plus `/dev/shm`, not capacity. CPU64 and NVMe leave `PYTHONHASHSEED` unset; CephFS sets it to zero.

The EPP also auto-created the **approximate** prefix producer in every run. With one backend replica, placement has no alternative destination, so this does not explain the performance difference; it does mean this batch cannot measure precise-EPP routing gains.

The Qwen TP=2 server exposes approximately 7.45 GiB of KV memory per worker and about 739,406 cached tokens per worker:

$$M_{KV,HBM} \approx 2 \times 7.45\ \text{GiB} = 14.90\ \text{GiB}$$

At a 131,072-token maximum context, that is approximately 11.28 full-context equivalents. Concurrency 32 therefore creates legitimate cache pressure without producing a persistent waiting queue in the successful tiered cell.
