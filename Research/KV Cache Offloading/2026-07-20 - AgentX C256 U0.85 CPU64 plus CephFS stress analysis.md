## Executive verdict

This run did push substantially more KV data into the CephFS-backed PVC: a freshly provisioned volume grew from 0 to 206,426,865,664 bytes, or **192.25 GiB**. That proves filesystem-tier stores happened.

It does **not** prove filesystem-tier reads or CephFS cache hits. Every direct Ceph pool/MDS/OSD and container-filesystem I/O query again returned zero series. The available vLLM counter measures CPU→GPU loads after data is present in the CPU primary tier; it cannot say whether those blocks originated in CPU memory or were promoted from CephFS.

The workload point is beyond the useful capacity knee. Relative to the otherwise similar C=128/U=0.90 run, concurrency doubled, mean tokens in flight rose 94.87%, waiting requests rose 159.84%, mean TTFT rose 170.07%, mean end-to-end latency rose 114.23%, throughput fell 10.24%, and the boundary-cancellation fraction increased from 7.43% to 16.91%. Meanwhile useful prompt-token reuse fell from 7.58% to 2.33% and CPU→GPU load volume fell 73.62%. This is **write-heavy cache thrash**, not evidence of useful CephFS readback.

Two configuration mismatches make the run unsuitable for the intended validation:

1. The actual model pod still runs **`vllm/vllm-openai:v0.23.0`**, not v0.24.0. The v0.23 filesystem path performs synchronous `os.path.exists` lookups on the scheduler thread; v0.24 introduced background batched lookup and relevant offload fixes.
2. The EPP effective configuration auto-created **`approx-prefix-cache-producer`**, not a precise producer. It also overrode the configured approximate block size from 16 to 64 tokens. There is only one model replica, so routing choice cannot explain the server-side slowdown, but the run must not be labeled a precise-EPP validation.

Lowering `gpu-memory-utilization` from 0.90 to 0.85 reduced GPU KV blocks from 3,240 to 3,098, only 4.38%, while demand doubled. It did not lower observed occupancy: average GPU KV use was 93.81% versus 94.09%, because occupancy is measured against the smaller available pool. In vLLM 0.23, this warning means the CPU offloading manager could not allocate enough free or evictable primary-tier blocks for a store:

$$
N_{\mathrm{free}} + N_{\mathrm{evictable}} < N_{\mathrm{new\ store\ blocks}}
$$

Tiering pins CPU blocks while asynchronous CPU→filesystem cascades are outstanding; concurrent CPU→GPU loads also pin blocks. The immediate failure is therefore **CPU primary-tier store admission**. A backlogged CephFS cascade is a strong candidate for why blocks remained non-evictable, but it is still an inference because pending-operation, pinned-block, and direct Ceph-latency metrics were not captured.

Increasing filesystem read workers from 16 to 32 did not improve readback: CPU→GPU volume fell by 73.62%. This is not evidence that 32 threads are intrinsically bad; it shows worker-count tuning cannot rescue an already overloaded, poorly observable v0.23 run.

## Root-cause verdict

The true root cause of the poor result and cancellations is **workload pressure beyond the service’s capacity knee, amplified by a too-small effective cache hierarchy and vLLM 0.23’s offload behavior**:

1. Doubling AgentX concurrency doubled the live token working set.
2. Lowering GPU memory reduced HBM KV blocks and forced more evictions.
3. CPU capacity stayed fixed at 64 GiB, so capacity per active request fell sharply.
4. The hierarchy became store-dominated; CPU→GPU reloads and actual prompt reuse collapsed.
5. CPU store admission repeatedly failed while the request queue sat around 217.
6. Requests accumulated until AIPerf cancelled 16.91% at the duration boundary.

This is workload-related, but **not merely random-seed noise**: the seed remained 42, theoretical reuse was high, and queue, tokens-in-flight, transfer direction, prompt-source accounting, warnings, and boundary state all agree. Agentic branching can change individual request paths, so repetitions remain necessary, but it cannot plausibly explain the entire 2.7× TTFT increase alongside the measured pressure signals.

It is not possible to call this an NVMe/CephFS performance failure. Direct Ceph telemetry is absent. CephFS cascade latency may be part of the store-admission mechanism, but the experiment did not measure it.

## Correct next experiment

1. **Fix the deployment before changing workload pressure:** pin and verify vLLM v0.24.0 or newer from the running pod digest, and configure/verify the precise EPP producer from startup logs. With one replica, EPP mode is not performance-relevant; use multiple replicas if routing behavior is itself under test.
2. **Return to U=0.90 and C=96 or 128.** Do not lower GPU memory or increase concurrency again yet. Select the highest point with a bounded queue, no boundary cancellations, and no sustained cannot-store flood.
3. **Keep CPU at 64 GiB for the first corrected mechanism test.** Use a deliberate fill/drain/replay sequence: write more than 64 GiB of unique KV, wait for filesystem writes to drain, then replay prefixes known to have fallen out of CPU. Normal mixed AgentX traffic does not guarantee this readback phase.
4. **Make CephFS reads an acceptance gate.** Capture client read/write bytes and IOPS, MDS requests/latency, OSD latency, filesystem lookup hit/miss, filesystem read/write bytes and latency, pending read/write tasks, and pinned CPU blocks. A retained PVC footprint alone is insufficient.
5. **Compare CPU64 and CPU64+CephFS with identical phase ordering.** Require external-token reuse in the CephFS arm to exceed CPU-only, direct filesystem reads above zero, and no queue/storage saturation.
6. **Only after readback works, sweep capacity/pressure.** A sensible sequence is C=96/128/160 at U=0.90, then CPU=32/64 GiB. Lower U to 0.85 only as a later stress point, not as the proof-of-function point.
7. **Repeat each accepted point at least three times.** Report confidence intervals; do not compare this run’s 0.629 requests/s to clean offload tiers as if it were valid steady state.

## Acceptance criteria

- actual vLLM v0.24+ and intended precise/approximate EPP mode verified from logs;
- model and router zero restarts and zero HTTP errors;
- direct CephFS read bytes or read IOPS above zero during the replay phase;
- filesystem-tier read-hit/load counter above zero;
- no sustained `cannot store blocks` warnings;
- bounded waiting queue and zero duration-boundary cancellations;
- same seed, trace ordering, topology, U, CPU bytes, and two-phase timing between controls;
- at least three repetitions.
