# 2026-07-25 — Gemma 4 31B IT AgentX standardized offload matrix (batch 2)

## Executive summary

This is a four-cell, standardized comparison of HBM-only, 64 GiB CPU tier, 64 GiB CPU plus local NVMe, and 64 GiB CPU plus tuned CephFS. All cells use the same Gemma-4-31B-it FP8 deployment, TP=4 on four H100s, `gpu-memory-utilization=0.85`, 131,072-token context, 200 GiB `/dev/shm`, AgentX/WEKA workload, seed 42, and a 1,800-second profiling window.

This matrix is not a valid performance comparison. HBM-only and CPU-only completed only 2 and 3 sessions, while NVMe and CephFS completed zero sessions. The apparent rates are artifacts of requests that remained in flight and repeated offload failures, not steady-state serving throughput. The CPU-tier cells reached roughly 87% mean KV occupancy, but the secondary-tier cells emitted `cannot store blocks` failures and never established a usable workload path.

## Deployment and observability audit

| Cell | Tier configuration | Secondary storage | `/dev/shm` | Restarts | Tracebacks / CUDA OOM |
|---|---|---|---|---:|---|
| No offload | HBM only | none | 200 GiB | 0 | 0 / 0 |
| CPU 64 GiB | TieringOffloadingSpec, 64 GiB CPU | none | 200 GiB | 0 | 0 / 0 |
| CPU 64 GiB + NVMe | TieringOffloadingSpec, 64 GiB CPU | hostPath NVMe `/mnt/nvme-kv-cache` | 200 GiB | 0 | 0 / 0 |
| CPU 64 GiB + CephFS tuned | TieringOffloadingSpec, 64 GiB CPU | PVC `vllm-kv-cache`, tuned read/write threads | 200 GiB | 0 | 0 / 0 |

The dominant signal is failure, not storage performance: KV occupancy averaged 84–87% and peaked at 98–100% in every cell. NVMe produced 37 `cannot store blocks` events across 8 request IDs; CephFS produced 273 across 12 request IDs, with up to 59 retries for one request. CephFS PVC usage averaged 47.4%, but no CephFS pool/MDS throughput counters were exported.

## Interpretation and hypotheses

1. **This run is saturated and invalid for ranking tiers.** KV occupancy is near capacity and queues remain active, but the tiered backends fail to store blocks. First fix the offload path and rerun a short correctness/soak test before comparing throughput.
2. **CPU-only is the only cell that made limited progress, but it is still incomplete.** It completed three sessions and had zero logged server errors, yet the finite run leaves 29 sessions incomplete; do not treat 0.063 req/s as a capacity result.
3. **NVMe is broken at the KV-store layer in this run.** Its 37 cannot-store-block events and zero completed sessions make the reported 0.0019 req/s meaningless. Inspect capacity, permissions, path mounting, and block-store error responses.
4. **CephFS is worse and shows a retry storm.** It logged 273 cannot-store-block events, 119 profiling warnings, and a maximum of 59 retries for one request; zero sessions completed. This points to a store/write or block-addressing failure, not slow CephFS bandwidth alone. The available PVC metric confirms storage use, but missing CephFS pool/MDS operation series limits a direct filesystem-throughput conclusion.
5. **Model pods did not crash, but the benchmark failed functionally.** There were no tracebacks or CUDA OOMs; nevertheless, offload-layer errors prevented completion. The benchmark must be marked failed.

## Recommended next experiment

Hold the deployment and `/dev/shm` constant, increase concurrency in steps (32, 64, 128, 256), and collect at least three repetitions per cell. Stop or mark the point when KV occupancy reaches the desired pressure band (for example 70–90% rather than 10%). Export NVMe device latency/queue depth and CephFS client read/write/MDS counters at the same 15-second cadence. This separates workload sizing from storage-medium effects and turns the current directional result into a causal offload curve.
