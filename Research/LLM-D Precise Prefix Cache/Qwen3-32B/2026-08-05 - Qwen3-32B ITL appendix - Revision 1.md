## Interpretation

The two cases track closely through the useful knee because the model-serving pods, not the renderer pods, determine delivered token capacity. The CPU-renderer run is marginally higher in peak total throughput, while the vLLM-render run has the lower TTFT tail at that operating point. At high offered load, both runs show the same saturation signature: incomplete requests dominate and successful throughput declines. The correct conclusion is parity within single-run uncertainty, with a possible tail-latency advantage for vLLM-render, not a categorical winner.

The next run should pin the llm-d commit SHA, repeat each topology at least three times, and add renderer CPU/queue telemetry. Use total token throughput and a defined TTFT/E2E SLO at the highest rate with at least 95% successful completion as the acceptance criterion.
