# 2026-08-05 - Qwen3-32B precise-prefix renderer report - Revision 1

## What differs between the deployments

The model-serving deployment is held constant: Qwen3-32B, eight TP2 H200 replicas, vLLM image digest unchanged, GPU memory utilization 0.95, and the same Guidellm synthetic workload. The tested variable is renderer placement. In the vLLM-render case, the render endpoint is served by the model pods. In the comparison case, three separate non-GPU CPU renderer pods tokenize/render requests before routing to the model pods. Both runs use llm-d main, but the exact commit SHAs were not retained in MLflow metadata.

The previous figure was misleading because it encoded Prompt/Output/Total as “Configuration” and did not encode renderer placement. The corrected figures below use color for the metric and line style for renderer configuration, so every point belongs unambiguously to one metric and one deployment.

## Executive summary

At the useful throughput knee (target 20 RPS), the three-CPU-renderer deployment reaches 6.03 successful requests/s and 49.76 total tokens/s; the vLLM-render deployment reaches 5.87 successful requests/s and 48.39 total tokens/s. This is a small 2.8% throughput gap from one repetition, not proof of a renderer regression. The vLLM-render case has lower TTFT P95 at that point (120.4 ms versus 138.7 ms). At high offered rates both deployments saturate and completion falls sharply, so the 60-RPS points are stress behavior rather than sustainable capacity.

Prefix-cache reuse is active in both runs, warming to approximately 99.4% hit ratio. No KV-offload transfer telemetry is present; this is a precise-prefix renderer experiment.
