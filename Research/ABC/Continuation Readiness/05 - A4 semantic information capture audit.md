The cached source was analyzed with `tools/costar/weka_information_ladder.py`.

| Candidate-set size p50 / p95 | 2 / 6 |
| Agent-class entropy | 0 bits (all markers are `Subagent`) |
| Exact next-event edges | 58,102 |
| Deployable request I3 coverage | 0 |
| Deployable request I4 coverage | 0 |

Interpretation:

- The corpus contains a real structural workflow signal: 1,697 subagent dispatch markers across 634 candidate groups.
- That signal is not a normal request-time semantic label. Marker events do not identify which subsequent normal requests belong to the child in the raw stream, and all observed marker classes collapse to `Subagent`; therefore class entropy is zero.
- The exact-next-event count is an offline upper bound. It is not evidence that an application knew the successor before admission.
- This is enough to test a structural I3/I4 *upper bound* and to measure whether workflow fan-out correlates with avoided secondary service. It is not enough to claim deployable lifecycle-aware retention.

The adapter and analysis are in:

- `tools/costar/weka_semantic_trace.py`
- `tools/costar/weka_information_ladder.py`
- `tools/costar/run_weka_information_ladder.py`
- `tests/tools/test_costar_weka_information_ladder.py`

The next offline experiment should join the structural candidate groups to the accepted c32/c64 oracle traces and compare candidate-aware retention against I1/TTL, with candidate timestamps treated as an upper bound. If that upper bound has no request-level value, stop semantic retention. If it does, the next live requirement is explicit producer-side lifecycle metadata.
