## Three deviations the code forced on guide 03

These are corrections to the guide, not shortcuts. Guide 03 should be amended to match.

### 1. Single-allocation `allow_eviction=False`, not two-phase reserve-then-consume

Guide 03 §3.4 specified `try_reserve_no_evict()` producing a reservation that `_initiate_promotion(..., reserved=…)` later consumes. Inspecting the code showed that path already allocates exactly once: `_initiate_promotion` calls `primary_tier.prepare_write` (an alias of `CPUOffloadingManager.prepare_store`), which allocates at `ref_cnt = -1` — in-flight, and already excluded from `evictable_blocks`. The only real problem was that `prepare_store` *may evict LRU victims* to make room.

So the fix is one flag, not a second allocation path:

```python
def prepare_store(self, keys, req_context, *, allow_eviction: bool = True):
    ...
    if num_blocks_to_evict > 0 and not allow_eviction:
        return None
```

Threaded through `_initiate_promotion(..., allow_eviction=False)`. Keyword-only with a default, so every existing caller is untouched. The guide's two-phase design would have introduced the double-allocation bug it was trying to avoid. Release on cancellation uses the existing `complete_store(success=False)`, which already frees not-ready blocks.

### 2. Terminal partition needs a `cancelled` class (and `shadow_submit`)

The six-class partition in guide 03 §3.5 has no home for a bundle whose residency already resolved RESIDENT but which is then killed by request completion, preemption, or cache reset. Folding those into `gate_reject` would make the gate-rejection rate a function of request-finish timing and corrupt the very signal V2.0 is meant to calibrate. The implemented partition is:

$$\mathrm{considered} = \mathrm{primary\_redundant} + \mathrm{secondary\_absent} + \mathrm{gate\_reject} + \mathrm{capacity\_skip} + \mathrm{submitted} + \mathrm{shadow\_submit} + \mathrm{lookup\_unresolved} + \mathrm{cancelled}$$

`considered` and exactly one terminal class are incremented together at a single write point (`_finalize_keys`), so the invariant cannot be violated structurally rather than only by convention. A randomized multi-step simulation asserts it holds after every step across 12 seeds.

### 3. Lead time is derived from first-schedule events, not admission events

`ScheduleEndContext.new_req_ids` means *first scheduled*, not *admitted*. The estimator therefore measures the dequeue interval (EWMA over first-schedule events) and multiplies by queue position, where queue position is the count of admitted-but-not-yet-first-scheduled requests tracked inside the policy. Both are observable from hooks the manager already receives — no core scheduler change.

A consequence worth stating plainly, because it is the mechanism V1 measured: **a request admitted to an empty queue predicts H = 0 and is correctly never prefetched.** That is the concurrency-32 regime (mean waiting < 0.25, 98.50% late). Lead time has to exist before prefetch can help, and the gate now encodes that rather than discovering it at benchmark time.

> Later correction, from 06: queue position was initially counted only over requests
> carrying the per-request opt-in, so a marked request queued behind unmarked ones
> predicted H = 0. Every admission now feeds the queue estimate; bundles are still
> created only for opted-in requests.

## Other implementation facts worth recording

- **Minimum one-step lookup latency confirmed empirically.** The fs-tier end-to-end test traverses `PENDING_LOOKUP → PENDING_LOOKUP → SUBMITTED`: the async batch flushes at step end and drains no earlier than the next step. Guide 03 §3.7's "consumable in the same step" wording is wrong; `H_remaining` recomputation absorbs it.
- **`has_pending_work()` had to be extended.** It feeds `has_pending_push_work()` → `Scheduler.has_requests()`. Without including policy state, the engine quiesces and pending bundles never re-drive.
- **Cancellation is immediate, not deferred.** Tier finalization (and thus `AsyncLookupManager.cleanup`) is deferred while primary stores pend, so the policy hooks `on_request_finished` directly and drops the bundle from the active set — guaranteeing no lookup is re-issued after cleanup, which would leak `_req_keys` permanently.
- **V1 coexists and stays comparable.** V2 submissions still advance `PREFETCH_ATTEMPTED`/`PREFETCH_PROMOTED` and enter `_prefetched`, so V1's outcome chain (useful/late/wasted/load_failed) and both V1 accounting identities hold verbatim. Configuration validation rejects enabling both.
- **Bundle truncation.** A resolved run longer than `max_promotions_per_step` is truncated, with the excess counted `capacity_skip`; the submitted prefix stays contiguous from the frontier, which is the only form the demand scan can consume. *(Later revised: see 06 §10 — truncating on step contention discarded work permanently and is now a deferral.)*

## Flaw-class → guarding test

93 tests added across four files (`test_admission_prefetch_policy.py`, `test_admission_prefetch_manager.py`, plus additions to `test_tiering_offloading.py`, `test_manager.py`, `test_fs_tier.py`, `test_scheduler.py`).

| Flaw class | Guard |
|---|---|
| Double allocation | `prepare_store` spy asserts one allocation per key |
| Speculative eviction | Full tier of evictable blocks stays intact; bundle → `capacity_skip` |
| Pending counted as absent | RETRY keeps `PENDING_LOOKUP`, zero `secondary_absent` |
| Deadline races | Expiry-while-pending, same-step resolve+expire, monotonic no-resurrection |
| Async-lookup leak | No lookup re-issued after finish; tier state clean |
| Accounting drift | Randomized 12-seed partition invariant + V1 identity preservation |
| Engine stall | `has_pending_work` covers pending bundles |
| Scheduler-loop cost | Terminal bundles dropped; idle steps do no per-bundle work |
| Preemption mid-lookup | Cancels unsubmitted, leaves submitted alone |
| Finish while SUBMITTED | Promotion completes cleanly, no KeyError |
| Tracker overflow | `prefetch_track_capacity=1` keeps both partitions closed |
| reset_cache with pending | Drain-then-reset; provenance assert passes |
| Config validation | Mutual exclusion, unknown keys, type/range rejection, shadow default |
| Shadow side-effects | Zero allocations, zero V1 counter movement |
| Real async path | fs-tier end-to-end with genuine thread handoff |

Full suite: 724 passed, 9 skipped across the kv_offload and offloading-connector suites. The 56 failures in `test_gpu_worker.py` / `test_shared_offload_region.py` are pre-existing on the base branch (verified by stashing) and environment-related. `pre-commit` clean including mypy.

## How to enable

```json
{
  "kv_connector_extra_config": {
    "spec_name": "TieringOffloadingSpec",
    "cpu_bytes_to_use": 274877906944,
    "secondary_tiers": [{"type": "fs", "root_dir": "/mnt/kvcache", "n_read_threads": 16}],
    "prefetch": {
      "enabled": true,
      "policy": "admission",
      "shadow_mode": true,
      "max_pending_bundles": 256,
      "max_promotions_per_step": 64,
      "max_candidate_chunks": 1024
    }
  }
}
```

Per-request opt-in remains `kv_transfer_params.abc_admission_prefetch: true` (strict `is True`). Set `admission_prefetch_chunks` instead of `prefetch` for the V1 baseline cell; enabling both is rejected at startup.

New metrics: `vllm:kv_offload_tiering_prefetch_admission_{considered, primary_redundant, secondary_absent, gate_reject, capacity_skip, submitted, shadow_submit, lookup_unresolved, cancelled}` (label `tier`), plus `..._bundle_outcomes` (`tier`, `outcome`), `..._transitions` (`transition`), and the `..._lead_time_seconds` histogram.
