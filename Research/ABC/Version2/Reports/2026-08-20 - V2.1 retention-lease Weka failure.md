# V2.1 retention-lease Weka failure

## Executive summary

[Run 7d56be15](https://mlflow.apps.psap-automation.ibm.rhperfscale.org/#/experiments/359/runs/7d56be15fa04496db9ef76c7b539b235?workspace=benchflow) is the first live Weka run of the physical-reserve plus one-bundle retention lease implementation. The rendered manifest, application metrics, and native Prometheus artifacts agree that the new image and policy were active:

- image: `quay.io/rh-ee-aperdomo/vllm:v0.27.0-prefetch-v5`;
- live prefetch enabled, 64 promotions/step and 64 chunks/bundle;
- physical speculative reserve: 512 blocks;
- retention lease: one bundle.

The new mechanism does submit, promote, and lease speculative data. It is therefore a stronger result than the earlier zero-promotion allocator failure. But its performance is still catastrophically poor and the mechanism is not useful enough to justify its I/O cost: useful rate averages 0.389 blocks/s while wasted rate averages 7.573 blocks/s. Demand-critical activity also reclaims leased blocks at 3.888 blocks/s on average. This run rejects the current retention policy as a performance candidate.

## Validity verdict

# Invalid for benefit analysis; valid as a mechanism failure diagnosis

The session finished and emitted the required telemetry, so the failure is observable rather than an instrumentation gap. It is not valid evidence of prefetch benefit: request throughput is 0.261/s and mean TTFT is 48.1 s. That is essentially the same severe failure regime as the prior non-retaining physical-reserve run ([493bcd6a](https://mlflow.apps.psap-automation.ibm.rhperfscale.org/#/experiments/359/runs/493bcd6ad3e741789339e9a1a6f6e543?workspace=benchflow): 0.262/s, 47.1 s). It is far below the healthy stock reactive reference [4111b847](https://mlflow.apps.psap-automation.ibm.rhperfscale.org/#/experiments/359/runs/4111b847dba14ae0a8f6b6617aec939e?workspace=benchflow): 0.671/s and 8.42 s mean TTFT.

## Prefetch and lease evidence

The data plane is live. Admission, attempted, and promoted all average 8.118 blocks/s (maximum 11.615 blocks/s), so selected bundles reach the Weka-to-CPU promotion path. The lease gauge reaches 64 blocks—the configured one-bundle limit—and averages 21.17 blocks.

That is not enough to make the promoted copies useful:

| Native metric, 5-minute rate query | Average | Peak | Interpretation |
|---|---:|---:|---|
| promoted / attempted / admission submitted | 8.118 blocks/s | 11.615 | Promotion data path is active |
| useful | 0.389 blocks/s | 1.349 | Only a small fraction of proactive copies is consumed by later demand |
| wasted | 7.573 blocks/s | 11.378 | Most proactive copies do not survive to useful demand |
| late | 0 | 0 | A first demand did not observe an in-flight promotion; this is not an overlap problem |
| evicted before demand | 2.574 blocks/s | 4.299 | Explicit pre-demand eviction remains frequent |
| leased speculative blocks | 21.17 blocks | 64 | One-bundle lease is being applied |
| lease reclaimed by demand-critical work | 3.888 blocks/s | 6.4 | Demand-critical activity often overrides the lease |

Integrated prefetch outcome samples report 4.71% useful and 93.29% wasted. `evicted_before_demand` is a diagnostic subset/event stream, not an additional mutually-exclusive terminal class; its 31.71% integrated value shows that ordinary capacity pressure is a material source of the waste.

Source: native vLLM Prometheus JSON, sampled at 15-second cadence; the rate metrics use the stored five-minute Prometheus window.

The run remains heavily backlogged:

|---|---:|---:|
| Queue time p50 | 112.7 s | 720.0 s |
| Queue time p99 | 247.6 s | 955.2 s |
| Tiering async lookup mean | 15.08 s | 42.38 s |
| Latest tiering async lookup mean | 41.31 s | — |

These are not minor tail effects. The queue-time distribution and growing async-lookup duration are consistent with costly prefetch plus reactive work competing on the storage/CPU path. They support, but do not alone prove, the causal inference that low-value promotion traffic drives the service collapse.

## Causal interpretation

The v5 change repaired the immediately-discarded-copy behavior only partially:

```text
Weka → CPU promotion → speculative copy leased (works)
                         ↓
demand-critical CPU allocation requires capacity
                         ↓
lease is reclaimed in 64/128-block chunks
                         ↓
copy is evicted before later demand, or ultimately wasted
```

This is a policy failure, not an oracle proof failure. A lease that can be routinely overridden by pressure does not create a usable predictive cache under this workload. Conversely, making leases non-reclaimable without a carefully bounded capacity budget risks harming reactive demand even more.

The key point is that we must not continue N/concurrency sweeps yet. They would measure the same high-waste transfer loop more intensely.

## Required next change and acceptance gate

1. **Separate retention from demand-critical borrowing.** Keep the existing reactive-correctness fallback, but do not admit a speculative bundle unless it has a bounded protected budget that demand-critical work will not routinely reclaim. If that guarantee cannot be made at 512 blocks, reduce admission and reserve the budget at the scheduler level instead of generating a transfer likely to be destroyed.
2. **Bound and observe the lifetime.** Track a promoted bundle through one exclusive terminal accounting path: useful, expired, cancelled, failed, or evicted-before-demand. Record the allocator reason for a lease reclaim.
3. **Add an integration test across the real manager path.** Promotion succeeds → lease exists → realistic ordinary GPU→CPU persistence occurs → selected key remains a CPU hit until demand or a declared bounded expiry.
4. **Run one Weka control/treatment pair, not a sweep.** Proceed only when all gates hold:
   - promoted > 0 and useful is materially non-zero;
   - waste is no longer close to promoted;
   - evicted-before-demand and demand-critical lease reclamation are rare;
   - queue and async lookup latency do not regress versus a node-paired reactive control;
   - all expected requests finish successfully.
