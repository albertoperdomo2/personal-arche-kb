# V2.1 first five-cell comparison

## Executive verdict

**V2.1’s admission selector, asynchronous residency pipeline, terminal accounting, lead-time estimator, deadline gate, and transfer-cost calibration are running. The live V2.1 cell, however, submitted zero speculative blocks.** This batch therefore validates most of the control plane and validates the non-evicting safety behavior, but it does **not** yet validate the live prefetch data plane or a performance benefit.

The decisive sequence is:

1. Shadow mode identified **171 gate-approved bundles / 10,832 keys** that it would have submitted.
2. Live mode resolved **166 resident bundles**. One was rejected by the deadline comparator; of the remaining 165, **33 had become primary-redundant** by the manager recheck and **132 hit the non-evicting allocation refusal on their first missing key**.
3. Consequently, live emitted **0 `admission_submitted`, 0 V1 `prefetch_promoted`, 0 useful, and 0 wasted**. Its **132 V1 attempted = 132 skipped** confirms that it reached the manager but never allocated a destination block.

This is a useful negative result. The safety contract prevented V2.1 from evicting demand-owned CPU KV. The V1 N=100 control did evict and blindly load assumed-resident keys; it collapsed to **0.258 requests/s**, logged **67 missing-file I/O failures during profiling**, and made only **1,641 of 18,144 initiated promotions useful**.

The four safe cells—stock reactive, overlay reactive, V2.1 shadow, and V2.1 live-with-zero-submissions—cluster closely. V2.1 live is slightly worse or mixed in this single run, but because it moved no speculative data this is policy/measurement overhead plus run variance, not evidence for or against prefetch benefit.

## Experiment matrix and validity

All cells used AgentX Weka replay at concurrency 64 for 1,800 seconds, seed `20260707`, `first_turn_prefix` cache busting, a 128k context cap, 256 GiB CPU KV, one local NVMe filesystem tier with 64 read and 64 write threads, and request gate `kv_transfer_params.abc_admission_prefetch=true`. Every AIPerf result reports no HTTP errors and `submission_valid=true`; every model pod had zero restarts.

Stock versus overlay on the same node passes the first regression screen: overlay changes are within roughly ±2.6% on the shown central/tail metrics, with throughput within +0.2%. Shadow versus live on the same node is also close except for mean/median TTFT: live mean TTFT is +5.7% and median TTFT +11.5% versus shadow. One run per cell cannot separate V2.1 scheduling overhead, node state, and trace variance.

V1 is qualitatively different: versus overlay it loses 61.7% request throughput, mean TTFT rises 478%, and mean ITL rises 245%. It also performs about 49% more NVMe load bytes per completed request and spends roughly 7.8× more asynchronous lookup time per completed request. This is consistent with cache churn, failed blind loads, and reactive work waiting behind speculative work—not a benign slow-tail fluctuation.

Two interpretation cautions matter:

- `capacity_skip` is not currently a pure CPU-capacity metric. It combines the tail trimmed by the policy’s 64-key hard cap with manager allocation refusal and other budget paths. Bundle outcomes and the V1 compatibility counters are needed to identify the live allocator failure.
- `gate_reject` includes resolved prefixes of bundles that became late before lookup completion as well as the single fully-resolved `gate_reject_deadline` bundle. The bundle-outcome label is the clean comparator-level signal.

## Why live V2.1 submitted nothing

The live path calls `prefetch_submit()`, which calls `_initiate_promotion(..., allow_eviction=False)`. `CPUOffloadingManager.prepare_store()` then accepts only **truly free** block-pool entries; it will not consume normal evictable demand blocks. The AgentX warmup had already populated the 256 GiB CPU cache, so the pool had no free slots even though the existing `cpu_cache_usage_perc` gauge looked low.

That gauge is easy to misread. Its numerator subtracts evictable ready blocks, so it measures non-evictable active/write-pending occupancy, not total physical allocation. A low value therefore does **not** imply free speculative capacity. The live run’s maximum gauge was only 15.8%, yet every one of the 132 first missing keys was refused because the remaining blocks were allocated and merely evictable.

The batch-abort behavior explains the counter sizes: after the first missing key fails allocation, the manager classifies the rest of that 64-key prefix as admission `capacity_skip` without incrementing the V1 attempted counter for every tail key. Thus **132 attempted = 132 skipped**, while thousands of admission keys are capacity-terminalized.

This is a safety success and an opportunity failure. Simply changing back to `allow_eviction=True` would recreate the V1 failure mode.

## What is working, what is not

**Working:** request/policy gating; disabled-cell isolation; primary-frontier scan; ordered asynchronous secondary lookup; late/absent/resident transitions; exact per-key terminal partition; shadow no-transfer behavior; online transfer-cost fit; deadline instrumentation; non-evicting live safety; reactive fallback; failure attribution in V1.

**Not yet working as a POC:** live proactive transfer, live completion outcomes, usefulness measurement, TTFT/throughput benefit, and a capacity metric that distinguishes hard-cap trimming from physical allocation refusal.

**Working but needs refinement:** the lead-time estimator is directionally close but tail calibration should be evaluated; about 6% lookup-unresolved share shows the asynchronous oracle can still miss the opportunity window; shadow mode overstates feasible submission because it does not model the primary allocator’s lack of free slots.

## Next steps

### P0 — make capacity and success auditable

1. Split `capacity_skip` into reason-labelled counters: policy hard-cap tail, max-pending-bundle cap, step budget, speculative-byte cap, manager no-free-slot, and manager recheck redundancy.
2. Add CPU gauges for total allocated, truly free, evictable demand, speculative ready, read-pending, and write-pending blocks. Keep the existing active-usage gauge but rename/document it so it cannot be mistaken for free capacity.
3. Add a benchmark acceptance gate: a live mechanism cell is invalid for benefit analysis unless `admission_submitted > 0`, submitted promotions reach a terminal completion outcome, the terminal partition balances, and no demand-owned eviction is attributed to speculative work.

### P1 — create safe speculative headroom

4. Reserve a bounded speculative block budget before warmup fills the CPU cache. The run reports 131,072 CPU blocks for 256 GiB, or 2 MiB per logical block; a first mechanism sweep of 64, 256, and 1,024 reserved blocks corresponds to about 128 MiB, 512 MiB, and 2 GiB.
5. Keep demand data non-evictable by speculative work. If replacement is needed, allow speculative work to reclaim **only older speculative blocks**, never ordinary demand-owned blocks.
6. Treat a transient no-free-slot result as deferrable until the bundle deadline when a reservation exists, with strict per-step and in-flight bounds. The current first refusal terminalizes the bundle immediately.

### P2 — rerun for correctness before performance

7. Repeat stock, overlay, shadow, and live with the reservation sweep. Keep V1 only as a short negative safety control.
8. Require: nonzero submitted/promoted; zero blind missing-file loads; no speculative demand eviction; successful completions; useful > 0; no stale in-flight state; exact terminal accounting; and bounded queue/transfer contention.
9. Run at least three randomized repetitions per accepted cell, paired by node where possible. Only after those gates pass should TTFT and throughput be compared as performance evidence.
