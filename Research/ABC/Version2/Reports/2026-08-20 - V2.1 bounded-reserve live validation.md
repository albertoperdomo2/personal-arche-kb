# V2.1 bounded-reserve live validation

## Executive summary

This is an **interim live-only checkpoint** after the first V2.1 report exposed zero truly free CPU blocks. The implementation added a bounded reserve, exact capacity-reason metrics, and CPU physical-occupancy gauges. The configured live cells did load the corrected V2.1 configuration—rather than relying on their MLflow revision tags—but they again submitted **zero** speculative promotions.

The new telemetry explains why. At the moment a residency-verified, deadline-approved 64-key prefix reached the allocator, the CPU cache was physically full: free_blocks=0, fill=1.0, and speculative_blocks=0. The reserve was still reported as configured and unused (reserve=64, reserve_free=64), proving it was a logical accounting limit rather than 64 physical slots protected from ordinary cache stores.

A matched V2.1 shadow run will be added to this report when available. Until then, this document evaluates the live allocator/data-path checkpoint only.

## Validity verdict

# Invalid for benefit analysis; valid as a negative allocator diagnosis

The required correctness gate, admission_submitted > 0, was not met in either V2.1 live cell. No conclusion about TTFT or throughput benefit is valid. The runs are nevertheless decisive evidence that the current reserve implementation does not retain physical speculative headroom through warmup.

## Causal diagnosis

The current design separates allocation modes correctly at the speculative call site: speculative promotion uses SPECULATIVE_ONLY and therefore will not evict ordinary demand-owned CPU data. That safety property held.

The problem occurs earlier. The scheduler's normal GPU→CPU persistence path calls prepare_store() with the default ANY allocation mode. When that path cannot preserve the unused reserve without refusing its own bulk cache store, the demand-protection fallback may borrow the reserve. Warmup eventually fills those final slots.

The resulting state is:

~~~text
configured reserve = 64
logical reserve-free = 64
physical free blocks = 0
speculative blocks = 0
eligible live prefix → SPECULATIVE_ONLY allocation → refused
~~~

This is why the policy reaches pending_lookup → resident → capacity_skipped, records alloc_refused, and never reaches resident → submitted. The safety invariant is preserved, but the POC's required data-plane invariant is not.

## What is working

- The rendered configuration proves that corrected V2.1 live mode—not V1 and not a tag-selected mode—was deployed.
- The per-request HTTP gate is present and the V2.1 metrics are emitted.
- The admission state machine found resident prefixes; the failure is downstream of selection.
- bundle_trim is now visible, as intended, and shows that the 64-chunk ceiling is binding for much of the candidate window.
- The allocator does not evict ordinary CPU data for speculative work.
- Both live repetitions independently reproduce the same allocation failure.

## What is not established

- No live NVMe→CPU speculative promotion completed.
- No useful, late, wasted, or load-failed speculative completion outcome can be evaluated.
- No TTFT or throughput benefit can be attributed to V2.1.
- This batch is not a valid performance comparison because the reactive control is anomalously slow and placement differs.

## Smallest next change and run

Do **not** sweep N yet. First make the reserve physically enforceable through warmup.

The allocator needs three distinct contracts:

1. **Normal GPU→CPU cache persistence:** respects reserved physical slots; it may defer or decline a non-critical cache store instead of consuming speculative headroom.
2. **Speculative promotion:** consumes only those protected slots, or replaces only ready speculative blocks.
3. **Reactive demand promotion:** may borrow the reserved remainder as a last resort when needed to serve an active request.

Add an integration-style regression test that drives the real scheduler persistence path until the CPU cache is full, then asserts that at least N physical free blocks remain and that the first eligible speculative bundle submits.

After that fix, rerun one node-paired reactive-overlay/live 64/64/64 pair. Accept the run for performance analysis only if:

- admission_submitted > 0;
- prefetch_promoted > 0;
- speculative blocks rise above zero;
- at least one submitted transfer reaches a terminal completion outcome;
- no speculative eviction of ordinary demand data is observed;
- the terminal partition balances.
