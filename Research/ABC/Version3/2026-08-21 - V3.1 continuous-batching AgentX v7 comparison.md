# ABC V3.1 continuous-batching AgentX comparison — v7 severe regression

## Executive summary

This experiment tested whether ABC Version 3.1 speculative prefetch improves AgentX under continuous batching with max_num_seqs=8. It compared reactive CPU/NVMe tiering against the same deployment with ABC enabled. Both used the same image digest, model, TP8 topology, profile, dataset, seed, concurrency 64, 256 GiB CPU tier, and 64/64 NVMe workers.

The treatment is a severe negative result. Request throughput fell **55.0%**, output-token throughput fell **59.1%**, mean TTFT increased **125.8%**, mean end-to-end latency increased **130.9%**, and mean ITL increased **180.3%**. Prefetch was active and approximately 48% of submitted chunks became useful, but that did not produce end-to-end utility.

## Validity verdict: Conditionally valid negative result

This pair rejects the current v7 configuration as tested, but it is not sufficient to estimate a stable causal effect or abandon speculative prefetching:

- Manifests differ only in generated names and the treatment prefetch block. Pod state confirms both model containers ran digest sha256:890cd1760333ccbad3da63adb9df96f705230b6bc3be2ba635a09855f914e297.
- Both 30-minute client runs completed with no request errors or cancellation. Both sustained eight running sequences and zero preemptions.
- There is one run per configuration on different H100 nodes. Starts were 20 minutes apart despite parallel launch and overlapped for about 11 minutes.
- The treatment NVMe export contains both model nodes. Resource values below explicitly filter to each model pod's own node, but storage telemetry is not a perfectly isolated causal trace.
- GPU utilization, GPU memory, and PCIe artifacts are empty.
- Cache cleaning state was not recorded. Identical first_turn_prefix cache busting does not prove identical initial NVMe state.

## Main takeaways

- **Measured:** request throughput was 0.163 versus 0.362 requests/s, a 55.0% regression.
- **Measured:** mean TTFT rose 125.8%; mean ITL rose 180.3%; server generation rate averaged 213 versus 622 tokens/s.
- **Measured:** client prompt-cache-read share was not worse: 93.54% treatment versus 92.94% control.
- **Measured:** submitted, useful, and wasted rates were 2.02, 0.97, and 1.00 chunks/s. Evicted-before-demand was 0.65 chunks/s and is a subset of wasted work.
- **Measured:** observed CPU, own-node NVMe, and CPU-to-GPU transfer activity were lower in treatment, not saturated.
- **Inference:** the ITL and generation-rate collapse points toward engine/scheduler interference or an unobserved GPU-side difference rather than simple NVMe bandwidth saturation.
- **Conclusion:** do not rerun or tune this v7 treatment unchanged. Isolate idle-policy overhead from active speculative I/O first.

## Conclusion

The current continuous-batching configuration is **not worth pursuing unchanged**. It preserved approximately 48% useful speculative work but caused a severe end-to-end regression.

The evidence does not yet justify abandoning speculative prefetching entirely. One cross-node pair cannot separate implementation interference from node variance or unobserved GPU behavior. The next step is a bounded causal diagnostic, not parameter optimization.

## Proposed next steps

### 1. Build an immutable post-review image

Build the corrected code under a new tag such as v0.27.0-prefetch-v8 and record its digest. Include multi-slice fixed-cost charging, bounded expired-bundle cleanup, and stop-after-MISS behavior. Do not overwrite v7. These are correctness gates, not a predicted cure.

### 2. Add causal telemetry

Export:

- prefetch policy step wall time, calls/s, and activation scan length;
- admission frontier keys scanned and secondary lookups issued;
- demand versus speculative filesystem queue depth, active workers, bytes, operations, and latency;
- owner active time and deferral reasons;
- scheduler iteration duration and KV connector hook time;
- GPU SM utilization, memory bandwidth, PCIe, and clocks;
- cache-clean/reset evidence and image digest.

### 3. Run a three-arm diagnostic at max_num_seqs=8

Use the same node in counterbalanced order where possible, clean or fingerprint NVMe state, and repeat each arm at least three times:

1. Reactive control.
2. Idle-policy control: configure prefetch but remove request-level abc_admission_prefetch opt-in.
3. Bounded active treatment: restore opt-in with max_bundle_chunks=8 and max_promotions_per_step=8.

This uses the existing request opt-in and does not reintroduce shadow mode.

Decision logic:

- If arm 2 regresses, investigate idle policy/manager wiring or configuration side effects.
- If arm 2 matches control but arm 3 regresses, active lookup/I/O/cache interaction is responsible.
- If arm 3 is neutral but 64 chunks regresses, test 8/16/32 chunks.
- If the regression does not reproduce on the same node, perform a node crossover before making a mechanism claim.

### 4. Acceptance boundary

Do not resume benefit tuning until treatment:

- keeps request and output throughput within 5% of control;
- keeps mean and P95 ITL and TTFT within 5%;
- shows no demand-read or scheduler-step regression;
- remains active with useful share above the failed V2.1 level;
- reproduces across at least three repetitions and a node crossover.
